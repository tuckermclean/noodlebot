# U02 — daily-log

| Track | Deps | Unlocks | Size |

**Owns:** in `scheduler/report.py`: finding or opening the day's log issue, its body (the status table), its first comment (the morning overview), its event comments, the daily rollover (closing summary, closing, opening the next, pinning), closing the old status issue, and the answers it still takes on the log and the old status issue; the README's section on watching the loop; their cases in `scheduler/report.test.sh`.
**Resolves:** #23

## Purpose
After this node the sticky status issue, which grows without end, is replaced by one log issue per day. The day's issue, "noodlebot log YYYY-MM-DD" (the machine's local date) labelled `noodlebot-status`, has a body with a status table that the loop edits each tick. Its first comment is the morning overview, posted when the issue is opened, so it notifies the owner (body edits do not). Its other comments are the day's events, one line each. At the first tick after local midnight the loop posts a closing summary, closes the issue and opens the next day's, with links both ways. Per-unit detail lives on the unit issues (U01), and the old status issue is closed with a link to the first daily issue.

## Tests
- `scheduler/report.test.sh` (extended): `report.py` runs with a fixed local date (an environment override of "now" for tests) against the fake `gh api`. Cases: the first run with an open old status issue opens today's log issue and closes the old one with a link; the overview posted once as the first comment, the body's status table, the table edited on a later run with no second overview comment; events posted one line each, with no question and no closing summary in full; the rollover at the first run on a new date (summary, closing, new issue, links both ways, pin and unpin tried) done once, also after a failed call halfway; a failing pin call that changes nothing else; the owner closing today's issue; a prefixed answer on the log issue and on the old status issue while a question posted there is open.

## Changes
1. **The day's issue.** `report.py` uses the open issue labelled `noodlebot-status` titled "noodlebot log <today>" (local date), recorded in `report.json`. When there is none it opens one, with a link to the previous day's issue if there was one. If the owner closes today's issue, the next run opens a new one for the same day, linked from the closed one. *U02-AC-1, U02-AC-4.*
2. **Its body and the morning overview.** When the issue is opened, the loop posts the morning overview as its first comment, before any event: the previous day's summary (as in change 4), what waits on the owner, and the nodes `ready.py` would start next. A comment notifies the owner and a body edit does not, so the overview is a comment. The body is a status table, edited in place on each run under the existing rule (on a change, or every 15 minutes): the running sessions, what waits on the owner (each a link to its unit issue), the throttle and usage, and the deployed commit (the live checkout's HEAD). *U02-AC-2.*
3. **Its comments.** The day's status-log events, as now, but one line each: a session's end gives its total cost on that line and no closing summary, and no question is posted in full (U01 posts it on the unit's issue). *U02-AC-3.*
4. **The rollover.** At the first run whose local date is later than the open log issue's, `report.py` posts on it a closing summary: the PRs merged and opened that day, the units that wrote FAILED, and the summed cost of the sessions that ended that day. It closes that issue, opens the new day's linking it, and adds a link to the new one on the old. It tries GraphQL `pinIssue` on the new issue and `unpinIssue` on the old; a failure is logged and nothing else changes. `report.json` records each step, so a run that fails halfway finishes the rollover on the next run without doing any step twice. *U02-AC-4.*
5. **The old status issue goes.** An open `noodlebot-status` issue that is not a log issue (the sticky status issue) is closed, with one comment linking today's log issue. Prefixed answers posted on it (`B03: ...`, `#46: ...`) are still taken as long as a question posted there before the switch is open; prefixed answers on the log issue are taken as on the status issue now. *U02-AC-5.*
6. **Pinning, checked.** Whether the n00dl3b0t App may pin an issue is found out once, by a real run, and recorded in the node's PR. Either way the README's "Watching it" section links the repository's open `noodlebot-status` issues, which always lists today's issue. The loop changes no README and no repository setting. *U02-AC-6.*

## Risks
- "The morning overview (what MORNING.md has today)" in issue #23 refers to a file that is not in this repository; the overview here is built from what the loop knows (the previous day's summary, what waits, what is ready next). The owner may want other content.
- If the App may not pin, today's issue is found through the previous day's link, the label's list and the README link. For repositories other than noodlebot, only the first two, because the loop changes no README or repository setting there.
- The day follows the machine's local time zone; a time-zone change or a clock jump can roll over twice or skip a date (each date's issue is still opened at most once).
- Cost totals stay the CLI's list-price estimate, summed by the sessions' end time. A session that runs over midnight counts on the day it ends.
- The old status issue's last open questions are answered there with the prefix; questions after the switch are on unit issues only (U01).
