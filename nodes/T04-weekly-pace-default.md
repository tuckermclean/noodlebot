**Resolves:** #277

## Purpose
After this node the loop's throttle holds for the weekly pace unless it is told not to. T03 made the 7-day pace hold opt-in (`USAGE_7D_PACE=1`), and `loops.sh start` passes the setting to the loops it starts, so the hold lives only in the environment of the `start` that had it: a later `loops.sh start` from a shell without it, or a fresh machine, turns it off without a word. Now the loop runs `usage.py` with `USAGE_7D_PACE=1` when its own environment does not set it, so a plain `loops.sh start` keeps the hold, and `USAGE_7D_PACE=0` still turns it off. The margin stays `USAGE_7D_MARGIN` (default 0.10). `usage.py` run on its own keeps T03's default (off unless set), so T03's frozen cases hold. The README's Tuning table gives the new default, and the status issue and `status.sh` say whether the weekly pace hold is on.

## Changes
1. **The loop's default is on.** `loop.sh` runs the throttle's `usage.py` call with `USAGE_7D_PACE` set to the loop's own value when that is set and not empty, and to `1` otherwise (`USAGE_7D_PACE=${USAGE_7D_PACE:-1}` on that call). The setting is given to that call only: the loop's environment, and so the sessions', the deploy's and every other child's, is unchanged. Any value other than `1`, `0` included, keeps the pace hold off, as `usage.py` already reads it. The comment at the call says so. *T04-AC-1, T04-AC-2.*
2. **`usage.py` keeps its own default.** `usage.py` is not changed beyond its docstring, whose `USAGE_7D_PACE` line says that the loop passes `1` unless its environment sets the variable, and that a run by hand without it keeps the hold off. T03's cases of `usage.test.sh`, which run `usage.py` with the variable unset and expect no pace hold, keep passing. *T04-AC-3.*
3. **The status issue says whether the weekly hold is on.** `report.py`'s Usage section gets one line after the Throttle line, from `usage.json`'s `limits`: `- **Weekly pace hold:** on (holds new sessions while the 7-day window is more than N% ahead of pace)`, N from `seven_day_margin`, when `seven_day_pace` is `true`, and `- **Weekly pace hold:** off (\`USAGE_7D_PACE=0\`)` when it is `false`. With no `seven_day_pace` key the line is left out. Every other line of the section is as before. *T04-AC-4.*
4. **`status.sh` says so too.** Its `usage:` line ends with `, weekly pace hold on (margin N%)` or `, weekly pace hold off`, from the same fields, and with neither when `usage.json` has no `seven_day_pace`. The rest of the line, and of the screen, is as before. *T04-AC-5.*
5. **The README says so.** The Tuning table's row reads that `USAGE_7D_PACE` defaults to `1` (on) and `0` turns the weekly pace hold off, with `USAGE_7D_MARGIN` at `0.10`; the Tuning paragraph's example becomes `USAGE_7D_PACE=0 scheduler/loops.sh start`; the `HOLDING:` row's 7-day clause says "the week is ahead of pace (unless `USAGE_7D_PACE=0`)". *T04-AC-6.*

## Risks
- The pace hold holds early and hard right after a weekly reset, the reason T03 turned it off by default; the 5-hour throttle still paces each window. A machine that should not hold for the week needs `USAGE_7D_PACE=0 scheduler/loops.sh start`.
- A running loop picks the default up at its next deploy re-exec (D01), because the new `loop.sh` reads it: loops started without `USAGE_7D_PACE` turn the hold on then, with no restart, and loops started with `USAGE_7D_PACE=1` see no change.
- `usage.py` run by hand without the variable, as by the tests, still reads the hold as off and writes `seven_day_pace` `false` into `usage.json` until the loop's next tick writes it again. Only the loop and the tests run it today.
- The loop's environment does not gain `USAGE_7D_PACE`, so a session sees what it saw before; a tool that reads the setting from its environment rather than from `usage.json` (none today) would not see the default.
- The API, `nbctl.py status` and the status site are not changed; they show the throttle's hold and reason as before.
