**Resolves:** #106

## Purpose
After this node, a self-deploy that has CI configured never runs `make test` on the scheduler's machine. It deploys a runtime commit of `main` once that repository's CI workflow has passed that exact commit. The suite then no longer runs at load 30–40 under a 600 s timeout, a timing flake on this machine no longer rejects a commit CI passed, and a tick is not held up for ten minutes. A short local smoke check (shell syntax, Python compile) stays, because it catches what CI's runner cannot: an interpreter on this machine that differs from CI's. Without the configuration, the deploy runs `make test` as D01 and D04 say, so an installation without CI and the existing deploy tests keep working.

## Tests
- `scheduler/deploy-d07.test.sh` (new, in the style of `scheduler/deploy-d04.test.sh`: a fake remote of the scheduler's own repository, the live checkout as a clone, `make test` stubbed per commit and recording each call): a temporary `HOME` with `.config/noodlebot/deploy-ci` and a fake token script, and a fake `gh` on `PATH` that answers the workflow-runs request from a per-sha fixture and records each call with its arguments and whether `GH_TOKEN` was set. Cases: a runtime commit whose run succeeded; one whose run failed; one whose run is in progress and later succeeds; one with no run and later a successful one; a non-runtime commit; a failing `gh`; a malformed configuration; a commit with a shell syntax error and one with a Python syntax error whose runs succeeded; a rejected sha retried through `deploy/retry`; and the same remote without the configuration file.
- `scheduler/api-d07.test.sh` (new, in the style of `scheduler/api-p03.test.sh`, on its own root): `/v1/deploy`'s `last_failed` for a status log whose latest rejection is a CI or a smoke-check line.

## Changes
1. **The configuration.** `deploy.sh` reads the first line of `$HOME/.config/noodlebot/deploy-ci`, which has the form `<owner/name> <workflow file> <branch>` (for the scheduler's own installation: its repository, `test.yml` and `main`): the repository whose CI is read, the workflow, and the branch whose push runs count. When the file is missing or empty, the CI gate is off and every runtime range is tested with `make test` as D01 and D04 say, unchanged. When the line is malformed (not three fields, or no `/` in the first), `deploy.sh` deploys nothing, does not fall back to `make test`, prints one stderr line `deploy-ci: <reason>`, and exits 2. Nothing in `deploy.sh` names a repository, a workflow or a branch. *D07-AC-1, D07-AC-6.*
2. **The CI gate.** When the gate is on and the range `HEAD..origin/main` changes a runtime path (D04's list; a non-runtime range is fast-forwarded without CI as D04 says), `deploy.sh` reads the workflow's runs for the new `origin/main` sha (`gh api repos/<owner/name>/actions/workflows/<workflow>/runs` with `head_sha=<sha>`, `event=push`, `branch=<branch>`). It takes `GH_TOKEN` fresh from `$HOME/.config/noodlebot/token <owner/name>` on each run, never prints it, and runs under a timeout of 30 s. It never runs `make test`, and the newest of the runs decides:
   - **completed, `success`:** the smoke check (Change 3), then the deploy as on a `make test` pass. `deploy/previous` is recorded and the live checkout is fast-forwarded. A fast-forward that fails is remembered in `deploy/passed` and retried as D01 says. The status line is `deployed <old>..<new> (version <v>) after CI: <workflow> run <run id> passed`.
   - **completed, any other conclusion** (`failure`, `timed_out`, `cancelled`, `startup_failure` and the rest): rejected and recorded in `deploy/rejected`, with one status line `not deployed: <sha> (version <v>) fails CI: <workflow> run <run id> <conclusion>`, and not tried again.
   - **queued or in progress, or no run for that sha:** nothing is deployed or recorded as rejected, and `deploy.sh` exits 2 at once, so a later tick asks again. The first time a sha waits, one status line `waiting for CI: <sha> (version <v>) <workflow>` is printed and the sha is written to `deploy/waiting`. Every later wait for that sha writes only the stderr line `waiting for CI: <sha> <workflow> <queued|in_progress|no run>`.
   - **`gh` or the token script fails, times out or returns something that does not parse:** handled as a wait, but the stderr line names the failure and no status line is printed.

   A newer `origin/main` replaces the waiting sha. A rejected sha that `deploy/retry` puts back (P03) is read from CI again on the next run, so a CI run the owner re-ran and passed deploys. *D07-AC-1, D07-AC-2, D07-AC-3, D07-AC-4, D07-AC-5.*
3. **The smoke check.** Before a CI-passed sha is deployed, `deploy.sh` checks it out in a scratch worktree, as the `make test` path does. In the same clean environment, under a timeout of 60 s, it checks each tracked `*.sh` file under `scheduler/` and `plugin/` with `-n` of the interpreter its first line names (`sh` or `bash`), and compiles each tracked `*.py` file there with `python3 -I` without writing bytecode. The scratch worktree is removed afterwards. A file that fails rejects the sha (`deploy/rejected`), with one status line `not deployed: <sha> (version <v>) fails the smoke check: <file>` and the checker's message on stderr. A smoke check that times out or is killed is retried on later runs and counted as a timed-out `make test` is (D01's `$max_tries`). *D07-AC-4.*
4. **The API counts the new rejections.** `api.py`'s `last_status_lines` also takes a `not deployed:` line that contains ` fails CI: ` or ` fails the smoke check: ` as a failed deploy, so `/v1/deploy`'s `last_failed` (and `nbctl status`) shows it. The schema does not change. *D07-AC-7.*
5. **README.** One paragraph says what `~/.config/noodlebot/deploy-ci` holds, that the GitHub App must be able to read the repository's Actions, and that without the file the deploy runs `make test`. *D07-AC-1.*

## Gate
- **D07-AC-1** — With `deploy-ci` naming the repository, the workflow and the branch, a runtime commit whose newest push run on that branch for that sha concluded `success` is deployed: the live checkout moves to it, `deploy/previous` holds the old `HEAD`, one status line `deployed <old>..<new> (version <v>) after CI: <workflow> run <id> passed` is printed, the `make test` stub records no call, and the fake `gh` was called with the configured repository, workflow, branch, the sha and a `GH_TOKEN`. Without the file, the same remote runs the `make test` stub as D01 says. *Verify:* `scheduler/deploy-d07.test.sh`.
- **D07-AC-2** — A runtime commit whose run concluded `failure` (and one that concluded `cancelled`) is not deployed: one `not deployed: <sha> (version <v>) fails CI: <workflow> run <id> <conclusion>` line, the sha in `deploy/rejected`, no `make test` call, and a second run calls `gh` for it no more. *Verify:* `scheduler/deploy-d07.test.sh`.
- **D07-AC-3** — A runtime commit whose run is in progress, and one with no run yet, are not deployed or rejected. `deploy.sh` exits 2 within 35 s with no `make test` call, prints `waiting for CI:` as a status line on the first run only and on stderr on each run. Once the fixture reports `success`, the next run deploys it. *Verify:* `scheduler/deploy-d07.test.sh`.
- **D07-AC-4** — A CI-passed commit with a shell syntax error in a `scheduler/*.sh` file, or a Python syntax error in a `scheduler/*.py` file, is rejected with `not deployed: <sha> (version <v>) fails the smoke check: <file>`. A clean CI-passed commit's smoke check leaves no scratch worktree behind, and the live checkout gets no `__pycache__`. *Verify:* `scheduler/deploy-d07.test.sh`.
- **D07-AC-5** — A failing fake `gh`, and a failing token script, leave the live checkout and `deploy/rejected` as they were, exit 2 with a stderr line naming the failure, and print no token. A sha rejected for CI that `deploy/retry` puts back, with its run now `success`, is deployed on the next run. *Verify:* `scheduler/deploy-d07.test.sh`.
- **D07-AC-6** — A non-runtime range is fast-forwarded with D04's line `deployed <old>..<new> (version <v>) without make test: no runtime change` and no `gh` call. A malformed `deploy-ci` deploys nothing, runs no `make test`, and exits 2 with one `deploy-ci:` stderr line. *Verify:* `scheduler/deploy-d07.test.sh`.
- **D07-AC-7** — `/v1/deploy`'s `last_failed` is the latest `not deployed:` line when that line is a CI rejection or a smoke-check rejection, as it is for `fails make test`. *Verify:* `scheduler/api-d07.test.sh`.

## Risks
- The live installation turns the gate on only when the owner writes `~/.config/noodlebot/deploy-ci` (sessions never touch `~/.config/noodlebot/`). Until then the deploy keeps running `make test` locally.
- CI runs on GitHub's Ubuntu runner, not on this machine. Something that passes there and fails here only at run time (a different `awk` or Python behaviour, say) is deployed, and the smoke check catches only syntax. `deploy/rollback` (D01, P03) is the remedy.
- If push runs stop (the workflow disabled, Actions down, a `paths` filter added to `test.yml`), every runtime commit waits forever. `deploy.log` and the one `waiting for CI:` status line per sha are where the owner sees it. A non-runtime range still deploys.
- The newest `origin/main` is the only sha read. If `main` moves faster than CI finishes, the deploy waits for the tip and does not deploy an older passed commit.
- The GitHub App needs read access to Actions on the scheduler's own repository. Without it, `gh` fails and the deploy waits (D07-AC-5's path), so a missing permission shows up in `deploy.log`, not as a rejection.
- A cancelled run rejects its sha. When the owner re-runs it and it passes, `deploy/retry` deploys it.
