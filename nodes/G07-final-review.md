## Purpose
After this node the owner can take a node PR's last `Fresh review (<verdict>)` comment as the signal that the head it names is the one to merge. A node session fixes the findings it will act on before it posts its final review, so nothing follows that review on the PR (on #104 a follow-up RED and GREEN were pushed after "Fresh review (approve)", and the owner merged an unreviewed head). Every review the skill posts names the commit it covers, and a session that pushes to a PR after a review was posted says first that the review no longer covers the head and ends with a new final review of the new head. U04 builds the "ready to merge" state of the status issue and the site on these rules.

## Changes
1. **The final review is the last thing on the PR.** Step 6's fresh review on the PR says: findings the session will act on are fixed first (test-first: a new tester's RED, a new implementer's GREEN, the slice review), and then a **new** reviewer reviews the whole node at the final head. Only that review is posted with `<forge> pr comment`, its first line headed `Fresh review (<verdict>) at <sha>`, where `<sha>` is the head it reviewed (seven or more hex characters). A review whose findings will still be acted on is never posted headed `Fresh review (`: it stays in the session's notes (`out/node/<ID>/`), or is posted as a comment whose first line says the PR is not ready to merge. The session posts nothing to the PR after its final review but its own end (CI on that head, `QUESTION.md`); when CI on that head fails and the session fixes it, the push follows change 3. *G07-AC-1.*
2. **Every posted review names its head.** Every review comment the node skill posts (the fresh review, the resolution review, a review posted as not ready) names on its first line the commit it covers, as `at <sha>`: `Resolution review (<verdict>) at <sha>` for the merge commit it reviewed. *G07-AC-2.*
3. **A push after a posted review.** When a session must push to a PR that already has a posted `Fresh review` (a resumed session after an answer, a feedback session, an update session, a fix after CI failed), it first comments on the PR that the review at `<sha>` no longer covers the head and the PR is not ready to merge, then pushes, and ends by posting a new final review headed `Fresh review (<verdict>) at <new head>` from a new reviewer. That reviewer reviews the whole node when the node's own code changed since the reviewed head; otherwise (an update whose resolution kept both sides, which reruns no whole-node fresh review, G02-AC-4) it is given the diff from the reviewed head to the new head and checks that it changes nothing of the node's beyond that. The update procedure (`--update`) and the feedback procedure (`--feedback`) of `plugin/skills/node/SKILL.md` say this; G02's sentence on when the whole-node fresh review is rerun and G03's on rerunning it when the code changed stay. A session that pushes nothing posts no new review. *G07-AC-3.*
4. **The templates.** The end-of-run line of `scheduler/unattended.md` and `scheduler/unattended-followup.md` says the run ends when the PR is open, the last review posted on it is a `Fresh review (<verdict>) at <sha>` naming the PR's head, and CI on that head is green (or with `QUESTION.md` or `WAITING-PR`, as before). Both, and `scheduler/unattended-feedback.md` and `scheduler/unattended-node-update.md`, say that a run that pushes after a posted review follows change 3: the comment before the push, and a new final review naming the new head before the run ends. *G07-AC-4.*

## Risks
- The sessions follow these rules by reading them; nothing in the loop stops a session that posts a review and then pushes. U04's ready state is the check the owner sees: a head that no posted review names is never shown as ready to merge.
- An update or a feedback session now ends with one more reviewer than before (the diff review of change 3 when the node's code did not change), which costs a little more per update.
- Reviews posted before this node name no head (`Fresh review (approve)` alone). Under U04 their PRs read "still being worked on" until a new final review naming the head is posted.
- Other tests that check the rendered prompts (G05's, S11's) may match the end-of-run line's words. The change adds to that line rather than rewording it, and those tests must pass unchanged.
