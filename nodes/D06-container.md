## Purpose
After this node noodlebot runs as one container, pulled from GHCR instead of set up from a `git clone`. The image holds the toolchain, rootless podman for the containers sessions run, and a copy of noodlebot. On its first start the container puts the live checkout on its home volume and starts the loops from there. From then on D01 deploys exactly as it does on the machine: it tests a new `main`, fast-forwards the checkout, re-execs the loops without stopping a session, and can roll back. A compose file runs the container on one host, and plain Kubernetes manifests run it on a cluster as a single replica.

## Tests
- `container/entrypoint.test.sh` (new): the entrypoint with a temporary home, a fake image copy (a small Git repository with a tag), fake `loops.sh` and `tmux` that record their calls, and config folders with and without each required file. Covers the first start, a later start with a moved checkout, the refusals and the stop on `SIGTERM`.
- `container/container.test.sh` (new): reads `container/compose.yaml`, the manifests in `container/k8s/` and `.github/workflows/image.yml` with PyYAML (as `check-regime.py` does) and checks the structure each criterion names. It also reads the `Containerfile` and `.containerignore`, and checks the README's container section names each file and option it documents.
- `scheduler/loops-pidns.test.sh` (new): holds a real lock on a loop's `loop.lock` (and on `api.lock`) with the `flock` command, as a loop does, and runs each probe with `NOODLEBOT_PROC_LOCKS` pointing at an empty file, so `/proc/locks` has no line for the lock. Cases: `loops.sh status` shows the loop running, `loops.sh stop` waits for the loop's lock and sends `TERM` to the API server holding `api.lock` (its pid from the `/proc/<pid>` path), `site.py`'s and `api.py`'s probes see it; with the lock released, each probe says not held. A case also runs the probes under `unshare --user --map-root-user --pid --fork --mount-proc` where the runner allows it, and passes when `unshare` is refused; it is not the only case for any probe.
- The image workflow's job on the PR (not in `make test`, which needs no container runtime): builds the image, runs `make test` inside it, runs the smoke start described in AC-6, and validates the manifests against the Kubernetes API schema. The run's URL is recorded in the PR.

## Changes
1. **The image.** `container/Containerfile` builds from a slim Debian base. It installs what `make test` and the loops use: bash, git, gawk, python3 with PyYAML, `gh`, tmux, Node and the Claude Code CLI (pinned by a build argument, with its self-updater turned off), plus rootless podman with what it needs (`uidmap`, subordinate ids for the user, and a storage driver that works without root). It creates a non-root user `noodlebot` with its home at `/home/noodlebot`, the volume's mount point, and runs as that user. It copies the build context, a full clone with its tags (so `git describe` works for V01), to `/opt/noodlebot` and points its `origin` at the repository's https URL, taken from a build argument rather than named in the file. It installs `container/entrypoint.sh` as the entrypoint. `.containerignore` keeps everything but the repository's tracked files and its `.git` out of the build context. *AC-1, AC-2.*
2. **The entrypoint.** `container/entrypoint.sh` refuses to run as root. It checks that the config folder `~/.config/noodlebot/` (mounted read-only) exists and holds `repos`, the token script and the harness's credential, and refuses, naming the first missing one. When `~/gitrepos/noodlebot` does not exist, it clones `/opt/noodlebot` there and sets `origin` to `/opt/noodlebot`'s `origin` URL. When it exists, it leaves it as it is, whatever commit D01 has moved it to. When the config folder holds a `gitconfig` file, `~/.gitconfig` includes it (`include.path`), so sessions commit with the owner's identity. It then runs `~/gitrepos/noodlebot/scheduler/loops.sh start` and stays in the foreground while the tmux server lives. On `SIGTERM` it runs `loops.sh stop` and exits 0. The runtime root stays the default, `~/.local/share/noodlebot` on the volume, outside any working tree, as D02 requires. *AC-3, AC-4, AC-5.*
3. **Nested rootless podman.** A session in the container can run `podman` as `noodlebot`, with no host socket mounted and without `--privileged`. The compose file and the manifests carry the device and security settings this needs, and the README says why each one is there. *AC-6.*
4. **One host: `container/compose.yaml`.** One service from `ghcr.io/<owner>/<name>:latest` with a named volume at `/home/noodlebot`, the host's config folder mounted read-only at `/home/noodlebot/.config/noodlebot`, the settings of change 3, `restart: unless-stopped`, a stop grace period long enough for `loops.sh stop`, and no published port. It works with `podman compose` and `docker compose`. *AC-6, AC-7.*
5. **A cluster: `container/k8s/`.** Plain manifests with a `kustomization.yaml` (`kubectl apply -k`, no extra tool), whose `images:` entry lets the owner name another image. The manifests define a StatefulSet with `replicas: 1`, a `volumeClaimTemplates` entry for `/home/noodlebot`, and the Secret `noodlebot-config` mounted read-only at `/home/noodlebot/.config/noodlebot`, with a mode that lets `noodlebot` run the token script. The Secret is created by hand from the config folder and is not in the manifests. They also define a pod `securityContext` that runs as `noodlebot` and allows change 3, and a termination grace period long enough for `loops.sh stop`. There is no Service, because the API is a Unix socket on the volume (`kubectl exec … nbctl`). *AC-8.*
6. **The image workflow: `.github/workflows/image.yml`.** On a pull request that changes `container/`, `.containerignore` or the workflow itself, it builds the image, runs `make test` inside it, runs the smoke start and validates the manifests, with `contents: read` only and nothing pushed. On a push to `main`, it does the same and then pushes `ghcr.io/<owner>/<name>` (lowercased from `github.repository`), tagged with the commit SHA and `latest`. Only that job has `packages: write`, and it logs in with `GITHUB_TOKEN` alone. The package's visibility is the owner's to set. *AC-1, AC-6, AC-9.*
7. **Docs.** The README's container section covers pulling the image and starting it with compose, building the config folder (and the Secret, `kubectl create secret generic noodlebot-config --from-file=…`), the optional `gitconfig`, and the settings of change 3 and why they are there. It also says that code deploys still go through D01 inside the container, that a new image (a new toolchain or CLI) takes a restart, which stops running sessions (S04 resumes them), that there is exactly one replica per runtime root, and that a repository whose builds need more tools gets a derived image (`FROM` this one). `SPEC.md` §2 and `AGENTS.md` name `container/`. *AC-10.*
8. **Lock probes in a pid namespace.** In a pid namespace other than the host's (every container, every pod), the kernel leaves out of `/proc/locks` each lock whose owner pid is not visible there. A loop takes `loop.lock` with the `flock` command, which exits at once, so inside the container the lock never appears in `/proc/locks`, and `loops.sh start`, `status` and `stop` (which the entrypoint runs on `SIGTERM`) and the probes of `site.py` and `api.py` miss a running loop. The same lock is listed, with pid 0, on a `lock:` line of `/proc/<pid>/fdinfo/<fd>` of each process that holds the file open. `held()` in `scheduler/loops.sh`, `held()` in `scheduler/site.py` and the probe `held()` in `scheduler/api.py` therefore, when `/proc/locks` has no line for the lock file's device:inode, also look for a `lock:` line with that device:inode (with the same device fallbacks) in `/proc/[0-9]*/fdinfo/*`. Three conditions hold:
   - the holder pid comes from the matched `/proc/<pid>` path, never from the 0 that fdinfo prints, so that wherever a probe's holder pid is used it names the right process: `loops.sh stop` sends `TERM` to the API server it finds holding `api.lock` (`api.py` itself signals nothing);
   - the fdinfo scan runs only when `/proc/locks` has no line for the file, and stays cheap, since on the host it runs on every negative probe (0.2 s wait loops, site ticks);
   - the probes read `/proc/locks` from the path in `NOODLEBOT_PROC_LOCKS` when it is set (used only by tests), so a test can present an empty `/proc/locks` with a real held lock.
   The rest stays as it is: the lock is never taken, and on the host, where `/proc/locks` lists the lock, nothing changes. *AC-1, AC-11.*

## Risks
- The fdinfo fallback of change 8 reads the fdinfo of every visible process on a negative probe. It runs only when `/proc/locks` has no line for the file, but on a host with many processes a probe in a wait loop costs more than before.
- The first push to GHCR happens only after the merge, on `main`. The owner checks that run, and sets the package's visibility by hand: the bot changes no settings.
- The manifests are validated against the schema but not run on a real cluster before the merge. Nested rootless podman in a pod depends on the cluster's runtime and policies (user namespaces, `/dev/fuse` or native overlay, seccomp and AppArmor profiles, Pod Security admission), which differ between clusters. A later node can add Helm and per-session pods in a namespace.
- Two schedulers for one repository start sessions twice: the container and the machine's own loops (or two replicas) must never run against the same `repos` at once. The smoke run uses an empty `repos` list for that reason.
- A new image (toolchain or Claude Code CLI) reaches a running scheduler only by a restart, which kills running sessions. S04 resumes them, but their in-flight work since their last commit is lost.
- The config folder comes from a read-only mount. Anything that writes into it (a token cache, say) fails in the container and must move elsewhere.
- Rootless podman's storage under the home volume needs a filesystem that supports its storage driver. Some volume types (NFS, say) do not.
- Host setup that the machine's loops rely on outside `~/.config/noodlebot/` (Git identity, other tools a target repository's builds need) has to be named in the README or the config folder. Anything missing shows up only when a session needs it.
