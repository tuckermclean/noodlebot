## Purpose
After this node a node session's end is logged "with a PR" or "no PR" only from PR lists whose fetch began after the session ended. Today `ended` judges a session the tick finds gone against the lists that same tick fetched at its start (`$open` and `$merged` for a fresh node, `open-prs.txt` and `merged-prs.tsv` for a follow-up, in `has_pr`), so a session that opens its PR and exits while the tick fetches its lists, or between the fetch and the tick's check of its sessions, is logged "no PR, no QUESTION.md; may start again" and started again, using one of its two starts. That is how S03-AC-5's check "(G01) a follow-up whose PR is open: its end is logged as ended with a PR" in `loop-s03.test.sh` (line 219 at this spec's base) failed in CI on spec-only PR #242 (run 45944516124, job 140326039263, head `6c6786c`), taking nine more checks with it; a real session that opens its PR just as a tick starts can hit the same race.

## Tests
- `scheduler/loop-s15.test.sh` (new, in the `Makefile`'s `TESTS`): an end-to-end loop with a fake forge and fake sessions that reproduces the race without depending on timing. A fake forge whose open-PR list call has read its list (without the session's PR) and returns it only after the fake session has opened its PR and exited (its `session.rc` written), so the session ends while the tick fetches its lists. Cases: a fresh node session that opens its PR that way; a follow-up session (FOLLOWUP marker, as S03) that opens its PR on its follow-up branch that way; a session that ends that way with no PR; a session that ended before the tick's fetch began (with and without a PR). Each case checks the status log's end lines, the node's `starts`, its sessions' run count and its worktree over the following ticks. Every wait in the file waits for the status-log lines, starts and ticks it checks, and a bound that stands for a number of the loop's ticks is counted in ticks (`wait_ticks`, D03's and D20's rule), never in seconds. A negative check reads its count only after the loop's ticks have visibly passed. The fake forge's wait for `session.rc` and each other wait have a give-up bound that fails its case with a `FAIL:` line instead of hanging the file. New helpers live in this file.
- `scheduler/loop-s03.test.sh`, unchanged: its check of line 219 and the checks after it hold in the loaded runs of Change 4.
- Every other `scheduler/loop*.test.sh` passes with the same `PASS:` lines at the node's base and head.

## Changes
1. **A node session's end waits for a list fetched after it.** The tick records when its PR lists' fetch began (before `pr_tsvs` runs). A node session (fresh or follow-up) that the running-sessions pass finds gone, and whose end is not older than that moment (its `session.rc` was written after the fetch began, or, with no `session.rc`, it was still running when the fetch began, which the tick knows only from an alive check of the session made before `pr_tsvs` runs), is left for the next tick: its `session.pid` stays, nothing is logged of its end, it is not started again and its worktree is not cleaned up or archived in this tick. The next tick, whose fetch began after the session ended, judges its end with `ended` as before. A session whose end is older than the fetch's start is judged in the tick that finds it gone, as before. A node session the tick itself stops (`stop_done`: its PR is merged or closed in this tick's lists) is judged in that tick, as before. The issue's suggested test (`session.rc` newer than `open-prs.tsv`) leaves the time the fetch runs uncovered, since `open-prs.tsv` is written when the fetch ends; the node may use another mechanism (a tick counter, say) if it shows the same outcomes. *S15-AC-1, S15-AC-2, S15-AC-3, S15-AC-4.*
2. **Other sessions' ends are unchanged.** Triage, update (of a spec PR or a node PR), adoption and feedback sessions, whose ends read no PR list, are judged in the tick that finds them gone, as before; the loop tests that cover them keep their `PASS:` lines. *S15-AC-7.*
3. **Reproduce it first.** `scheduler/loop-s15.test.sh`'s cases fail at the node's base on the "with a PR" and start-count checks of S15-AC-1 and S15-AC-2 (the RED), recorded in the PR with their `FAIL:` lines, and pass at the head. *S15-AC-5.*
4. **Show S03-AC-5's check holds.** On the scheduler's machine, with the load kept to half its CPUs (at least one) so that other sessions keep the rest, each run under one `taskset -c <those CPUs>` beside one CPU-bound process per pinned CPU, each bounded so that it cannot outlive its run (for example `timeout 900 yes >/dev/null`, killed when the run ends): ten runs of `make test TESTS=scheduler/loop-s03.test.sh` at the node's base (recorded: how many failed, on which check, with the status-log tail each failing run printed), and ten consecutive runs at the head, each run's log under `out/node/S15/`. `loop-s03.test.sh` is not changed; if the node finds a frozen line of it, or of a shared fixture, must change, the PR lists each one (file, base line, before and after, why) for the owner's approval, as U05's frozen-line record names them, and changes no expected value, pattern, order, count, event text or check name. *S15-AC-6.*
5. **Keep the budgets.** `loop-s15.test.sh` stays under `TEST_FILE_BUDGET` in an unloaded run (30 s) and in CI (`test.yml`'s `TEST_FILE_BUDGET`, 105 s at this spec's base); every other `scheduler/loop*.test.sh` keeps its `PASS:` lines; CI passes on the PR. *S15-AC-7.*

## Risks
- A session that ends during a tick now has its end judged, and its restart made, one tick later than before; a frozen loop test that waits a bound in seconds for such an end line or restart may need more time on a loaded runner. S15-AC-7 shows the files pass; a loaded failure of another file is not this node's to fix.
- The fetch's start is compared with file times (`session.rc`'s mtime, or a marker's); on a filesystem with coarse timestamps two events in the same second are equal, and an equal time must count as "not older" (left for the next tick), or the race comes back within that second.
- A session left for the next tick keeps its `session.pid`: whatever counts running sessions from pid files (`SCHED_MAX`, `turn.py`'s count, the API and the site) may count it one tick longer.
- `followup_done` does not check `session.pid`: a follow-up session left for the next tick whose PR is already merged in this tick's lists has its FOLLOWUP moved to `answered/` before the next tick's `ended` runs, so `has_pr` reads it as a fresh node (`$merged` holds its ID, so its end is still "with a PR"); only the order of those steps changes.
- The forge's lists can lag a PR just opened (an eventually consistent search, say), which a fetch begun after the session's end does not cover; the fake forge in the test answers at once.
- CI on a PR also enforces the total (`test.yml`'s `TEST_BUDGET`) and other files' timing, which slow runners break with no test change; a CI run that fails only on files this node does not touch is rerun, both run URLs recorded.
