**Owns:** in `scheduler/report.py`: the merge record of each open node PR in `report.json` (its head, the head and verdict of its last `Fresh review`, the CI result on its head) and the "Waiting on you" item of a node's open PR (ready to merge, or still being worked on and why); in `scheduler/site.py`, a node's `merge_ready` and `merge_why` fields; their keys in `scheduler/site-schema.json`; in `site/views.js`, the text a node with an open PR shows for them; the new tests `scheduler/report-u04.test.sh`, `scheduler/site-u04.test.sh` and `site/test/views-u04.test.mjs`, the two shell tests' lines in the `Makefile`'s `TESTS`, and any fixtures they add under `scheduler/testdata/u04/`.
**Resolves:** #105

## Purpose
After this node the status issue and the status site say a node's PR is ready to merge only when it is: no session runs on the node or on its PR, neither has a question (`QUESTION.md`), the forge does not report the PR as conflicting with its base, the PR's head is the commit its last `Fresh review` names (G07's `Fresh review (<verdict>) at <sha>`), that review approves, and CI on that head passed. Until then they say the node is still being worked on, and which of these is missing. On #104 the owner merged a head pushed after the final review, before any review or CI covered it; with this node that head would have read "still being worked on".

## Changes
1. **The merge record.** On each run, for each open node PR (a `node/<ID>-*` branch), `report.py` records in `report.json` the PR's head (from the PR list), the head and the verdict of the last comment whose first line is headed `Fresh review (<verdict>)` (the comments it already reads for U01's milestones; the head is the `<sha>` of `at <sha>` on that line, seven or more hex characters, or none when the line names none), and the CI result on the PR's head: `passed`, `failed`, `pending` (check runs not all complete) or `none` (no check runs, or none readable). The record is kept across runs, so a run that reads no new comment keeps the last review's head; a record whose head is not the PR's current head gets its CI result again. A failure to read is logged as `report.py`'s other failures are, and leaves the PR not ready. *U04-AC-1.*
2. **Ready to merge in the status issue.** A node's open PR is ready to merge when all of these hold: no session is alive in the node's state folder (`node/<ID>`) or in a node-PR update's or feedback's state folder of that PR (`pr/<N>`); neither folder holds a `QUESTION.md` (unanswered, or answered with the session that acts on the answer not started yet: either may still push); the PR's `mergeable` in `open-prs.tsv` (the fifth field) is not `CONFLICTING`; the PR's head starts with the head the last `Fresh review` names; that review's verdict is `approve`; and the CI result on the head is `passed`. The "Waiting on you" item that read "open, no session running on it (review or merge it)" then reads that the PR is ready to merge, naming the reviewed head; when `mergeable` is anything but `MERGEABLE` or `CONFLICTING` (`UNKNOWN`, `null`, empty: the forge has not computed it yet), the PR is still ready and the item adds that the forge has not said whether it merges cleanly. Otherwise, when no session runs and the node has no question, it says the PR is still being worked on and why: the PR has an open question (a `QUESTION.md` in `pr/<N>`, which the existing "PR #N asks a question" item also lists) or its answer waits for a session, the PR conflicts with its base, the head has no final review (naming the head and the head the last review names, or that there is none), the last review's verdict, or CI pending, failed or with no result on the head. With a session running there is no item, as before; the session is listed under Sessions. A node with a `QUESTION.md` or `WAITING-PR` in `node/<ID>` gets no PR item, as before; its own item is listed. *U04-AC-2.*
3. **Ready to merge on the site.** `site.py build` gives each node two fields: `merge_ready` (a boolean for a node in state `pr-open`, `null` otherwise) and `merge_why` (for a `pr-open` node that is not ready, the reason of change 2 in a short text; for a ready one whose `mergeable` is neither `MERGEABLE` nor `CONFLICTING`, the note that the forge has not said whether it merges cleanly; `null` otherwise). It takes the PR's head and `mergeable` from `open-prs.tsv`, the review and CI from `report.json`'s merge record (a record for another head counts as not reviewed), and the sessions and questions as change 2 does (`pr/<N>`'s `session.pid` and `QUESTION.md` too). Both keys are in `scheduler/site-schema.json`, and every text passes through the cleaning W01 gives all texts. *U04-AC-3.*
4. **The view.** In the repository view's node table, a `pr-open` node with `merge_ready` true shows "ready to merge", and its `merge_why` when there is one; one with `merge_ready` false shows "still being worked on" and its `merge_why`. No other node shows either text. *U04-AC-4.*

## Gate
- **U04-AC-1** — For each open node PR `report.py` keeps in `report.json` the PR's head, the head and verdict of its last `Fresh review (<verdict>)` comment (the `<sha>` of `at <sha>` on its first line, none when it names none), and the CI result on the PR's head (`passed`, `failed`, `pending` or `none`), kept across runs that read no new comment and taken again for a new head. *Verify:* `scheduler/report-u04.test.sh`.
- **U04-AC-2** — The status issue's "Waiting on you" says a node's PR is ready to merge only when no session is alive in `node/<ID>` or in that PR's `pr/<N>`, neither folder holds a `QUESTION.md` (answered or not), the PR's `mergeable` in `open-prs.tsv` is not `CONFLICTING`, the PR's head is the head its last `Fresh review` names, that review approves and CI on that head passed; a ready PR whose `mergeable` is neither `MERGEABLE` nor `CONFLICTING` is still ready, and the item says the forge has not said whether it merges cleanly. With no session running, no question in `node/<ID>` and any of the others missing, the item says the PR is still being worked on and names what is missing (an open question in `pr/<N>` or its answer waiting for a session, a conflict with its base, the unreviewed head, the verdict, or CI pending, failed or without result). In the #104 sequence (an approving review at one commit, then two pushed commits) the PR is not ready until a review names the last commit. *Verify:* `scheduler/report-u04.test.sh`.
- **U04-AC-3** — `site.py build` gives a `pr-open` node `merge_ready` true only under the conditions of U04-AC-2 (head and `mergeable` from `open-prs.tsv`, review and CI from `report.json`, sessions and `QUESTION.md` in `node/<ID>` and `pr/<N>`), else false with a non-empty `merge_why`; a ready node whose `mergeable` is neither `MERGEABLE` nor `CONFLICTING` has a `merge_why` saying so, any other ready node `null`; nodes in other states get `null` for both; the output passes `scheduler/site-schema.json`, which has both keys. *Verify:* `scheduler/site-u04.test.sh`.
- **U04-AC-4** — The repository view shows "ready to merge" for a `pr-open` node whose `merge_ready` is true (with its `merge_why`, escaped, when there is one), and "still being worked on" with its `merge_why` (escaped) for one whose `merge_ready` is false, and neither text for a node in another state. *Verify:* `site/test/views-u04.test.mjs` through `site/site.test.sh`.

## Risks
- The status issue and the site are only as fresh as their last run: a push made after a report run reads as ready until the next run sees the new head. The loop's tick bounds that delay; the site's publish interval adds to it.
- PRs whose reviews were posted before G07 name no head and read "still being worked on" until a new final review is posted.
- A repository whose forge gives no check runs never reads as ready to merge (CI `none`). The item says so, and the owner can still merge.
- `mergeable` is as fresh as the loop's last PR list, and the forge may report `UNKNOWN` for a while after a push or a change to the base; such a PR reads as ready with the note that its mergeability is not known yet.
- A node PR that changes frozen test lines (with the owner's approval, recorded in its PR) reads as plainly ready: nothing `report.py` or `site.py` reads (the state folders, the PR list, the review headings) marks it, so U04 does not say so; noting it is left to a separate issue.
- A comment headed `Fresh review (` by someone other than the bot counts as a review, as U01's milestones already count it.
- The API (`scheduler/api.py`, P01) still reports a `pr-open` node without the ready state; `nbctl` users see no change.
