**Resolves:** #39

## Purpose
After this node the owner's comments and reviews on the bot's own PRs are acted on, instead of being seen by no one. Each tick the loop reads the owner's conversation comments, line comments and reviews on every open PR the bot opened, and a PR with feedback newer than what was last acted on starts one session for the PR's unit: a node or follow-up PR gets a node session on the PR's branch, a spec PR a triage session on its spec branch. The session fixes what it can under the usual rules or asks the owner, replies to each point on the PR (what it changed, with the commit, or why not) and resolves the line threads it fixed. Feedback that arrives while it runs starts the next one.

## Changes
1. **What counts as feedback.** `scheduler/feedback.py` takes the tick's open-PR list (number, head branch, author, bot or not) and the owner's login. For each open PR by the bot it reads the conversation comments, the line comments and the reviews (`gh api`, every page). An item is feedback when its author is the owner (the owner's login with association OWNER, not a bot) and it is: a conversation comment; a line comment, whatever review it belongs to; or a review whose state is CHANGES_REQUESTED, or COMMENTED with a non-empty body. An approval, a review with an empty body (its line comments count on their own), a comment whose text is only 👍 (or `:+1:`, `+1`), anyone else's item and the bot's own are not. An owner comment that `report.py` recorded as the answer to a question of the PR's unit (its URL in that unit's `ANSWER.md`) is an answer, not feedback. *G03-AC-1.*
2. **The acted-on record.** `state/<name>/feedback/<N>` holds, for PR N, the newest conversation-comment, line-comment and review ID that has been handed to a session. `feedback.py` prints each PR that has feedback newer than its record, of any kind, and writes for it a `FEEDBACK.md`: the PR, its branch, and for each new item its kind, ID, URL, author, time and body, and for a line comment its file, line and thread. `feedback.py mark <N>` advances PR N's record to the items of the last `FEEDBACK.md` written for it; the loop runs it when it hands them to a session. On its first run (no `feedback/` folder) it records every open bot PR's newest IDs and prints nothing; a bot PR first seen later starts from an empty record. A failing `gh` call is logged, prints nothing for that PR, leaves its record unchanged and makes it exit non-zero; the loop logs that and carries on. The record of a PR that is no longer open is removed. *G03-AC-1, G03-AC-2.*
3. **The PR's unit.** A PR on `node/<ID>-<name>` or `node/<ID>-followup-<n>` belongs to node `<ID>`, and its session runs as that node's (`state/<name>/node/<ID>/`). A PR on `spec/*` is a spec-PR feedback task in `state/<name>/pr/<N>/`, as G01's updates are. Any other branch is skipped. *G03-AC-3.*
4. **Starting a feedback session.** When a PR prints, the loop appends its `FEEDBACK.md` to the unit's `FEEDBACK.md` (creating it), then advances the PR's record to the items handed over, sets the unit's starts to 0 and starts its session. A node: in its worktree (made on the PR's branch when it is gone, otherwise brought to `origin/<branch>`), running `/noodlebot:node --feedback <N>`. A spec PR: in `worktrees/<name>/pr-<N>` on the PR's branch, running `/noodlebot:triage --feedback <N>`, in the triage's slot as G01's updates are. The prompt is rendered from `scheduler/unattended-feedback.md`. Nothing is handed over and the record stays as it is while the unit's own session runs, while any session of `pr/<N>/` (an update of the same PR) runs, while the unit has FAILED or a QUESTION.md without ANSWER.md, or while the throttle holds; the feedback starts its session at the first tick after the hold ends. Feedback sessions count toward `SCHED_MAX` and take S07's turn as resumed units do. A start is one status-log event naming the unit, the PR, the number of items and the start count. *G03-AC-3, G03-AC-4.*
5. **How a feedback session ends.** An end with rc 0 and no QUESTION.md moves the unit's `FEEDBACK.md` into its `answered/` as `<ts>-FEEDBACK.md`, and the unit is not started for feedback again until new feedback arrives. An end with QUESTION.md keeps `FEEDBACK.md`; the answer is released as usual and the answered start carries on with it. A limit exit (or S02's background cut-off) uses no start. Any other end uses one of 2 starts, and the second writes FAILED. For a node, these rules replace the "ended with a PR" check while `FEEDBACK.md` is there, since its PR is already open. Each end is one status-log event. *G03-AC-5.*
6. **The prompt.** `scheduler/unattended-feedback.md` keeps the rules of `scheduler/unattended.md` (questions written to QUESTION.md and answered on the unit's issue, GitHub access with a fresh token per command, closing keywords, never merge, approve or push to `main`, the signature) and says in addition: the PR, its branch, the worktree, the path of `FEEDBACK.md` and the URL of each item in it, the skill command to follow, that every point gets a reply on the PR and that line threads it fixed are resolved. *G03-AC-6.*
7. **The node skill's feedback procedure.** `/noodlebot:node --feedback <PR> [--dry-run]` runs in a worktree on the PR's branch, brought to `origin/<branch>`. It reads `FEEDBACK.md`. A point that changes behaviour goes through the usual test-first steps (a tester's RED commit, the implementer's GREEN, the review); a point that would change, remove or rename a frozen test or fixture line, or change a spec file, is not made: it writes QUESTION.md with those points and its recommendation, after pushing and replying to the points it could settle. It never rebases or force-pushes. It reruns `make test` (the repository's test entry point) and the red targets the PR's criterion → evidence table names, reruns the whole-node fresh review when the node's code changed, and updates the PR body's table when its evidence changed. It replies to each point: a line comment in its own thread, the other points in one PR comment that links each; each reply says what changed, with the commit, or why nothing did. It resolves the line threads it fixed. It never approves, merges or dismisses a review. With `--dry-run` it stops before the push and writes `out/node/pr-<N>/result.md` with the commits and the replies it would post. *G03-AC-7, G03-AC-9.*
8. **The triage skill's feedback procedure.** `/noodlebot:triage --feedback <PR> [--dry-run]` runs in a worktree on the PR's named branch, brought to `origin/<branch>`. It changes the PR's specs as `FEEDBACK.md` asks, by the triage rules (graph first, current-state wording, a new node's ID from `nodes.py`'s next free line, never a merged node's criteria), as one new commit (never an amend, rebase or force push), and reruns the spec checker until PROBLEMS 0. A point that needs a judgment only the owner can make (a placement both ways reasonable, a principle or scope change) goes to QUESTION.md. It pushes, updates the PR's title and body when its nodes or criteria changed, replies to each point as the node skill does and resolves the line threads it fixed. With `--dry-run` it stops before the push and writes `out/triage/pr-<N>/result.md`. *G03-AC-8, G03-AC-9.*
9. **Questions of spec-PR feedback.** `report.py` posts a spec-PR feedback session's QUESTION.md once, as a milestone on its home issue: issue N for a PR on `spec/triage-<N>-*`, and the PR itself otherwise. The owner's comment after it there becomes its ANSWER.md, by U01's rule. A node's feedback questions are the node's, on its home issue, as for any node question. *G03-AC-6 (the prompt), G03-AC-10.*

## Risks
- Each tick reads three lists per open bot PR: more `gh api` calls under the App's rate limit. Reading only PRs whose `updatedAt` moved since the last read would cut them, if the limit is ever reached.
- An edited comment keeps its ID, so an edit after the comment was handed over is not seen; the owner writes a new comment instead.
- Feedback already on open PRs when this lands is not acted on (the first run only records it), so it does not replay comments settled by hand; the owner repeats what still matters.
- Any owner comment on a bot PR starts a session, including a note not meant as a request; the session can reply that nothing changes, at the cost of a session.
- G02's node-PR updates also start sessions on node PRs. They exclude each other through the node's session and `pr/<N>/`: G03-AC-4 holds feedback while an update runs, and G02-AC-1 holds an update while the node's session (a feedback session is one) runs. Whichever of the two merges second keeps both rules in its tests.
- The session's judgment (which points to fix, how, and what to reply) is shown only by the dry runs and by the replies on the PR, which the owner reads.
- Resolving line threads uses GitHub's GraphQL API with the App's token; if the App lacks the permission, the threads stay open and the replies still say what changed.
- The bot's replies notify the owner like any comment; they are the bot's own, so they never count as feedback.
