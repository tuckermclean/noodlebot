# U03 — queue-status

**Owns:** in `scheduler/turn.py`, the read-only `place` command (a unit's place in the machine's start order, taking no turn); in `scheduler/report.py`: the queued milestone of a labelled issue whose triage has not started, the start clause (the throttle and the units ahead) of the answer-received milestone, of the "Waiting on you" item of an answered unit and of the reply to a prefixed answer, a node's spec-PR-merged milestone, and leaving a unit whose spec PR is merged out of "Waiting on you"; the state of a node whose spec PR is merged in `scheduler/site.py`; the answered and spec-PR lines of `scheduler/status.sh`; in `scheduler/loop.sh`, listing the labelled issues every tick while the throttle holds; the new tests `scheduler/turn-place.test.sh`, `scheduler/report-queue.test.sh`, `scheduler/loop-u03.test.sh` and `scheduler/loop-u03-busy.test.sh` and their lines in the `Makefile`'s `TESTS`; their cases in `scheduler/site.test.sh`.
**Resolves:** #87

## Purpose
After this node what the bot says about a waiting unit is true while the throttle (T01) and the start queue (S07) hold it. The loop's report already runs every tick, but until a unit's session starts it says things that are stale or wrong. An answered question "resumes within seconds" while the throttle holds it for an hour. A node whose spec PR is merged still "waits for you to merge spec PR #N". A newly labelled issue hears nothing until its triage starts. Now, in the tick that sees it, a labelled issue gets one "queued" milestone. Each answer says what holds it and how many units are ahead of it. A merged spec PR moves its unit from "waits for you" to waiting for its turn. None of this uses a session or any of the plan's usage.

## Changes
1. **A unit's place in the queue.** `turn.py place <key> --repo <owner/name>` prints how many units are ahead of the key in the merged order `ask` would use (live loops only, starvation first), how long the key has waited and whether the gap has passed. A key that is not waiting prints `not waiting`. It reads the lists and the start record without the lock's write side and changes nothing. *U03-AC-1.*
2. **The start clause.** `report.py` builds one clause for a waiting unit from `usage.json` and `turn.py place`:
   - "resumes within seconds" (or "a follow-up starts within seconds") only when `ready.py` names the unit, no window holds, and the unit is first in the queue or there is no `waiting.json` (the queue is off);
   - otherwise what holds it: "the throttle holds new sessions (<the hold's reason>)" and/or "N units ahead in the start queue".

   S03's clauses for a unit that does not wait to start (FAILED, unmerged deps) are unchanged. When `turn.py place` fails, the clause is "it starts at its turn", with no count, and the failure goes to `report.log`. The clause is used by the answer-received milestone, the answered item of "Waiting on you", and the reply to a prefixed answer. A triage's answer gets it too, where today it gets no timing. *U03-AC-3, U03-AC-5.*
3. **Queued milestone.** For each issue in the loop's `issues.json` labelled by the owner, open, not triaged, and with no triage started (no `started` line for `#N` in the status log, this tick's included), `report.py` posts one milestone on the issue: "**Stage:** queued for triage". It says the start clause, or, when the issue is not yet waiting because another triage or update of its repository runs or waits, which one it waits behind. With the throttle holding, the loop still lists the labelled issues each tick (`issues.py next`), so `issues.json` is current. *U03-AC-2.*
4. **A merged spec PR is not waiting on you.** A node whose `WAITING-PR` names a PR in `merged-prs.txt` is left out of "Waiting on you". `report.py` posts one milestone on its home issue: "spec PR #N merged; <start clause>". `site.py` gives it the state `api.py` already gives (held, ready or waiting), not `waiting-pr`. `status.sh` prints "spec PR #N merged; waits for its turn" in place of "waits for you to merge". All of this happens in the first run after `merged-prs.txt` has the PR, before `release-markers.sh` moves the marker at the node's start. *U03-AC-4.*
5. **status.sh.** Its answered line says the same clause as the report (from `usage.json` and `turn.py place`), in place of "restarts at the next tick". *U03-AC-3.*

## Gate
- **U03-AC-1** — `turn.py place <key>` prints the number of units ahead of the key in the order `ask` uses across the live loops' waiting lists (a starved unit ahead of a smaller one, a stale loop's units left out), the key's wait, and whether the gap has passed. For a key not waiting it prints `not waiting`. A missing or malformed list is treated as `ask` treats it. The start record and every waiting list are byte-identical afterwards. *Verify:* `scheduler/turn-place.test.sh`.
- **U03-AC-2** — For an owner-labelled, open, untriaged issue whose triage has not started, `report.py` posts exactly one "queued for triage" milestone on the issue over any number of runs, in the first run that sees it in `issues.json`. With the throttle holding, it names the hold and its reason. With the throttle open, it gives the number of units ahead, or names the triage or update of its repository it waits behind. No queued milestone goes to an issue whose triage already started, an unlabelled issue or a triaged one. With the throttle holding and the start queue on, a newly labelled issue has its queued milestone within two ticks and no session starts. *Verify:* `scheduler/report-queue.test.sh`, `scheduler/loop-u03.test.sh`, `scheduler/loop-u03-busy.test.sh`.
- **U03-AC-3** — The answer-received milestone, the "Waiting on you" item of an answered unit (node or triage), the reply to a prefixed answer, and `status.sh`'s answered line say "within seconds" only when `ready.py` names the unit, no window holds, and the unit is first in the start queue or the queue is off. Otherwise each says what holds it: the throttle with its reason, and/or the number of units ahead. With no hold and no `waiting.json`, every text is as before this node, and the existing S03 and U01 cases pass unchanged. *Verify:* `scheduler/report-queue.test.sh`, `scheduler/report.test.sh`.
- **U03-AC-4** — In the first run after `merged-prs.txt` holds a node's `WAITING-PR`, "Waiting on you" has no item for the node, its home issue gets exactly one "spec PR #N merged" milestone with the start clause, `site.py` gives the node the state `api.py` gives (not `waiting-pr`), and `status.sh` does not say it waits for the owner's merge. A node whose spec PR is still open keeps today's texts and state. *Verify:* `scheduler/report-queue.test.sh`, `scheduler/site.test.sh`.
- **U03-AC-5** — When `turn.py place` fails, the texts promise no timing (no "within seconds", no count), the failure is one line in `report.log`, and the run and the loop carry on. *Verify:* `scheduler/report-queue.test.sh`.

## Risks
- The count of units ahead is a snapshot: a starved unit or a new triage can overtake later, and a unit's place can grow while it waits. The texts say "ahead" now, not when it will start.
- The queued milestone adds one comment per labelled issue that waits. An issue whose triage starts in the tick that first lists it gets none, only its started milestone.
- G03 (PR feedback) is still unbuilt and also changes `report.py`. Its feedback held by the throttle (G03-AC-4) gets no acknowledgement from this node or from S09; it waits for its session at its turn.
- If G04 merges first, the new milestone posts go through the forge interface, and the core check fails a direct `gh` call.
- `status.sh` now runs `turn.py`. On a machine whose loops are stopped, every list is stale, and it says the unit is not waiting.
