# M05 — loops-watchdog

| Track | Deps | Unlocks | Size |

**Owns:** in `scheduler/loops.sh`: the `watch` command, the `watch-unit` command (printing the system service and timer that run `watch`), the record of the settings `start` passes (`$NOODLEBOT_DATA/state/loops.env`) and of a stop (`$NOODLEBOT_DATA/state/loops.stopped`), the user watch timer `start` sets up and `stop` ends, the watch line of `status`, the usage line's new commands, and their lines in the header comment; in `scheduler/report.py`: the watch's events among the status-log events posted on the day's log issue, and the stale-loop comment on it; `scheduler/loops-m05.test.sh` (new) and its line in the `Makefile`'s `TESTS`; the README's lines on the watch.
**Resolves:** #218

## Purpose
After this node a loop or API server that died is started again within minutes, and a loop that hangs is reported, without the owner noticing first, even when the systemd user manager itself has gone. `loops.sh watch` starts each listed repository's loop and the API server that is not running, with the settings the last `start` passed, unless the owner stopped them, and the loops it starts outlive the watch run. It runs every few minutes from a system service and timer that `loops.sh watch-unit` prints (and never installs) for the owner to install, which run `watch` as the owner's user and survive a reboot and the end of the user manager; with M04's units file, `loops.sh start` also sets up a transient user timer for it, which is lost with the user manager. A loop whose lock is held but whose heartbeat is older than a limit is never killed; it is reported on that repository's log issue. Every restart is an event on the day's log issue.

## Changes
1. **The recorded settings.** `start` writes the settings it passes to each loop (T03's `USAGE_*`, `SCHED_*` and `PICKUP*` list) to `state/loops.env` (0600, one per line, written atomically) and removes `state/loops.stopped`; `stop` writes `state/loops.stopped`. *M05-AC-1, M05-AC-3.*
2. **`loops.sh watch`.** Under a lock of its own, it starts every listed loop whose lock is not held and the API whose lock is not held, as `start` does (through M04's `noodlebot-loops` scope when the units are on and the user manager answers) and with the recorded settings, unless `~/STOP`, `~/STOP-<name>` or `state/loops.stopped` exists; it writes the restart line to the repository's `status.log`. It leaves what it started running when it exits: no trap or wait of its own ends them, and the tmux server runs in a session of its own. A loop whose lock is held and whose heartbeat is older than `LOOPS_STALE` is noted in `state/watch.log`, never signalled. *M05-AC-1, M05-AC-2, M05-AC-3, M05-AC-6.*
3. **The reports.** `report.py` posts the watch's restart lines among the status-log events on the day's log issue, and once per stale episode one comment on the log issue for a stale loop the watch noted (a failed post is logged and tried again on the next run). *M05-AC-1, M05-AC-2.*
4. **The user timer.** With M04's units on, `start` sets up the transient timer `noodlebot-watch` with `--on-active` (a first run, without which `OnUnitActiveSec` never elapses for a service that has not run) and `--on-unit-active` of `LOOPS_WATCH_EVERY`, and `KillMode=process` on its service, running `loops.sh watch`; `stop` stops it; `status` says which watch timers are active. *M05-AC-4.*
5. **The system timer.** `loops.sh watch-unit` prints a system service and timer that run `loops.sh watch` as the calling user every `LOOPS_WATCH_EVERY` from boot, with the user's `HOME`, the runtime root, the calling shell's `PATH` and `XDG_RUNTIME_DIR`, and `KillMode=process`, so neither the end of a run nor the end of the user manager takes the loops it started; and the commands that install them. It installs nothing and changes no system setting; the owner installs the units once per machine. The README's watch lines show `watch-unit` in place of a cron line. *M05-AC-5.*

## Risks
- The user timer is transient: a reboot or a restart of the user manager drops it until the next `loops.sh start`, and with lingering off (M04's line) it does not run while the owner is logged out. The system timer from `watch-unit` survives both, once the owner installs it; until then the watch is only as durable as the user manager.
- `KillMode=process` keeps the loops a run started in the watch service's cgroup when the user manager is gone (M04's scope cannot be made then); they run outside `user@.service`, and their sessions then fall back to S12's OOM score alone, since no user bus is there for their scopes. The next `loops.sh stop` and `start` by the owner moves them back.
- `watch-unit` prints the calling shell's `PATH` and paths into the unit; a later move of the checkout or the runtime root needs the units printed and installed again.
- `loops.env` holds the settings, never a credential; `start`'s pass list has no credential variable (T03).
- A loop restarted by the watch takes over its running sessions as any restarted loop does (principle 2); a loop that keeps dying is restarted every few minutes, each restart an event the owner sees.
- The stale report needs the forge's token from the token script outside a loop; when that fails it stays in `watch.log` and on stderr (the timer's journal).
