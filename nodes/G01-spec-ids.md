## Purpose
After this node two spec PRs open at the same time do not give two new nodes one ID. The triage helper `nodes.py` reads the graph of every open `spec/*` PR as well as `main`'s, lists the IDs they add, and prints the next free ID of each letter. The triage skill takes a new node's ID from that line. When one of the bot's own spec PRs still conflicts with `main` after another PR merges, or `main` has meanwhile given one of its new IDs to another node, the loop starts an update session for it. That session merges `main` into the branch, renumbers its own new nodes whose IDs are now taken, reruns the spec checker, pushes and says on the PR what it did.

## Changes
1. **`nodes.py` sees open spec PRs.** It lists the open PRs whose head branch starts with `spec/`. For each it reads `docs/graph.yaml` from the PR's head branch, and prints the IDs it adds that `main` lacks, each with its PR number. Then it prints one `next free:` line with, for every letter in use, the number after the highest ID on `main` and in those PRs. When it runs on a spec branch, the PR of that branch does not count as another PR. Any of its new IDs that `main` or another open spec PR gives to a node of another name is printed as a clash. If the PR list or a PR's graph cannot be read, it prints that the IDs in open spec PRs are unknown, prints no `next free:` line and exits non-zero. It never falls back to `main` alone. *G01-AC-1, G01-AC-2, G01-AC-3.*
2. **The triage skill uses it.** A new node takes the `next free:` ID of its letter. When `nodes.py` cannot tell, the run ends without a PR, and a later start tries again. *G01-AC-4.*
3. **The update procedure.** `/noodlebot:triage --update <PR>` runs in a worktree of the PR's branch. It merges `origin/main` into the branch: a merge commit, no rebase and no force push. Any of the PR's own new nodes that `nodes.py` reports as a clash gets the next free ID: the file name, the graph entry, the AC IDs, the PR's own references and the header rows it changes in other specs all change with it. It reruns the spec checker until PROBLEMS 0 and pushes. It updates the PR's title and body to the new IDs and comments on the PR with what it merged, each renumbering (old → new) and the checker's result. It changes no criterion beyond the renumbering. When a conflict needs a judgment (two edits to the same criterion, say), it pushes nothing. It comments on the PR with the conflicting files and why, and ends. `--dry-run` stops after the local merge and renumbering and writes its result to `out/triage/pr-<N>/result.md`. *G01-AC-4, G01-AC-8.*
4. **The loop finds spec PRs that need an update.** The tick's open-PR list also gives each PR's number, author and `mergeable`. A PR needs an update when its head branch starts with `spec/`, its author is a bot (the loop's own App), and either GitHub reports it CONFLICTING or its branch's `docs/graph.yaml` (from the fetched clone) gives an ID of `main`'s graph to a node of another name. PRs in state UNKNOWN wait for a later tick. A failure of the list stops the tick, as it does now. *G01-AC-5.*
5. **The loop runs one update at a time, in the triage slot.** The update is started like a triage, with state in `state/<name>/pr/<N>/`, the prompt rendered from `scheduler/unattended-update.md`, a worktree `worktrees/<name>/pr-<N>` on the PR's branch, and `/noodlebot:triage --update <N>`. Only one triage or update runs at a time, so two updates never pick the same new ID. They are held by the throttle and `SCHED_MAX` like any session. A start is one status-log event, and the running note shows it as `PR #N`. *G01-AC-5.*
6. **How an update ends.** With rc 0 its worktree is removed and the loop records the `main` and PR-head commits it started from. It does not start that PR again until one of them moves. A limit exit gives its start back. Any other end uses one of 2 starts, and the second writes FAILED, which holds the PR until the owner deletes it. Each end is one status-log event. *G01-AC-6.*
7. **The status issue shows updates.** `report.py` treats `pr/<N>` like `issue/<N>`, as the task `PR #N`: running, and FAILED under "Waiting on you" with its reason and the path to delete. *G01-AC-7.*

## Risks
- The update session is a judgment call by Claude (resolving conflicts, renumbering references). Only the dry run in G01-AC-8 shows it, not `make test`. A careless resolution could still pass the checker with a wrong header row; the PR comment says what changed, for the owner to check.
- A spec PR renumbered after the issue's triage comment leaves that comment naming the old ID. The PR comment carries the new one.
- An update that can't resolve a conflict comments and ends with rc 0. If `main` moves again before the owner acts, it tries again and comments again.
- Node sessions also open spec PRs. Those are updated the same way when they conflict, but a node session that adds a node does not use `nodes.py`'s next free line unless its skill says so.
- Only the bot's own PRs are touched. A human's spec PR that takes an ID is left to the human, and a bot PR that merges second renumbers around it.
- `mergeable` is computed by GitHub lazily: a PR stays UNKNOWN until something asks, so an update can start a tick or two late.
- CI does not run the spec checker on the repository's own graph. A duplicate ID that merges cleanly is caught by the loop's clash check (Change 4), not by CI.
