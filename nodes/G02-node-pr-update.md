**Resolves:** #44

## Purpose
After this node a node PR of the bot's own that conflicts with `main` is brought up to date by an update session the loop starts, as G01 does for spec PRs, instead of waiting for the owner to merge `main` by hand. The session merges `main` without touching a frozen test or fixture line or a spec file (it asks the owner instead), reruns the tests, and pushes only once a fresh reviewer has checked the resolution: that both sides' intent survives and that test blocks from different nodes share no names or state. Every conflict resolution the skills make gets that review, and new test blocks keep their scratch paths in a folder of their own, so two appended blocks stop colliding.

## Changes
1. **The loop finds node PRs that need an update.** G01's search for PRs that need an update also takes a bot's open PR whose head branch starts with `node/` and that GitHub reports CONFLICTING (UNKNOWN waits for a later tick). The node is the ID after `node/` in the branch name (`node/<ID>-<name>` or a follow-up's `node/<ID>-followup-<n>`). It is skipped while that node's own session runs, and the node's session is not started while its update runs. A failure of the list stops the tick, as it does now. *G02-AC-1.*
2. **The loop starts node-PR updates.** Its state is `state/<name>/pr/<N>/` and its worktree `worktrees/<name>/pr-<N>` on the PR's branch, as for a spec-PR update. The prompt is rendered from `scheduler/unattended-node-update.md` and the session runs `/noodlebot:node --update <N>`. It has no ID to pick, so it does not take the triage's slot: it counts toward `SCHED_MAX` like a node session, is held by the throttle, and is queued by S07's turn as a spec-PR update is. A start is one status-log event. *G02-AC-1.*
3. **How a node-PR update ends.** As G01's updates end (rc 0 removes the worktree and records the `main` and head commits it started from; a limit exit gives its start back; a second end without rc 0 writes FAILED), and one more: an end with `QUESTION.md` is one status-log event and starts nothing more until the owner answers. The answer is released into `answered/` and the update starts again with its starts reset. *G02-AC-2.*
4. **Its questions go to the node's home issue.** `report.py` posts a node-PR update's `QUESTION.md` once, as a milestone on the home issue of the PR's node (U01's `node/<ID>/issue`), and takes the owner's comment after it there as the update's `ANSWER.md`. The update itself gets no home issue of its own. Status shows it as `PR #N`, running or FAILED, as G01's are. *G02-AC-3.*
5. **The node skill's update procedure.** `/noodlebot:node --update <PR> [--dry-run]` runs in a worktree on the PR's named branch. It brings the branch to `origin/<branch>` and merges `origin/main` into it: a merge commit, never a rebase or a force push. When a resolution would change, remove or rename a frozen test or fixture line (the repository's frozen paths) or change a spec file, it aborts the merge, pushes nothing, writes `QUESTION.md` with the conflicting files and lines and its recommendation, and ends. It may add lines to a test file only to keep two appended test blocks apart (for example clearing the first block's scratch paths before the second). It then reruns `make test` (the repository's test entry point) and every red target the PR's criterion → evidence table names. The resolution review (change 6) follows. Only then does it push, and comment on the PR: each resolved file and how, each added test line, the test results, and the review's verdict. It reruns the whole-node fresh review (step 6) only when the resolution changed the node's own code beyond keeping both sides. A failing test it cannot fix by resolving the merge is a `QUESTION.md`, with nothing pushed. With `--dry-run` it stops before the push and writes `out/node/pr-<N>/result.md`. *G02-AC-4, G02-AC-7.*
6. **Every conflict resolution gets a fresh review.** Whenever either skill resolves a merge conflict (the node skill's `--update`, its own merges of `origin/main` while building a node, and the triage skill's `--update`), a **new** reviewer (the repository's reviewer role) gets the merge commit and its diffs against both parents. It checks that both sides' intent survives, that test blocks from different nodes share no names or state (functions, variables, scratch paths, fake binaries), and that no frozen test line was changed, removed or renamed. Nothing is pushed before it approves. On `request_changes` the session fixes the resolution and a new reviewer checks it once more; a second rejection pushes nothing and ends with `QUESTION.md` (node skill) or a comment on the PR (triage skill). The verdict and findings are posted on the PR, headed `Resolution review (<verdict>)`, as a comment, never an approval. *G02-AC-5.*
7. **Test blocks keep their own scratch folder.** The node skill tells the tester that a test block it appends to a shared test file keeps its scratch paths (folders, remotes, state, fake binaries) under a folder named after the node (for example `$tmp/<ID>/`), so a block appended by another node cannot collide with it. *G02-AC-6.*

## Risks
- The update session is Claude's judgment (resolving conflicts, telling a frozen line from a new one). `make test` checks only the skill's text and the loop's handling; the dry runs in G02-AC-7 and the resolution review are the evidence that the judgment is sound, and the PR comment lists what changed for the owner to check.
- Node-PR updates no longer share the triage's slot, so several can run at once under `SCHED_MAX`, each running `make test`. On a small machine that slows the other sessions. S07's start gap still spaces their starts.
- A node PR waiting for the owner's merge is updated again each time `main` moves while it still conflicts. Each update is a session and a comment; two starts per `main` and head pair bound a stuck one.
- A conflict-free merge can still break the other side (two blocks far apart sharing a name). Only conflicting PRs get an update, and CI on the PR's head is what shows the rest.
- Older test blocks keep their shared scratch paths; the scratch-folder rule applies only to new ones, so appended blocks can still collide until those files are reworked (D03 touches them, but only for speed).
- The resolution review in the node skill's own merges of `main` adds a reviewer to some node builds; it runs only when the merge had conflicts.
