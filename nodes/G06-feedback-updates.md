**Owns:** in `scheduler/loop.sh`: the start of a node's feedback session taking the PR's branch back from a leftover node-PR update worktree (`worktrees/<name>/pr-<N>`) and putting a worktree the update detached back on the branch; the hold of a node's feedback while a node-PR update question of its PR is unanswered; the rule for an open-PR list as long as its limit in the cleanup of pending `FEEDBACK.md` files; in `scheduler/feedback.py`, the same rule for removing the record and file of a PR no longer open; the resolution review in the feedback procedure (`--feedback <PR>`) of `plugin/skills/node/SKILL.md`; their cases in `scheduler/loop-g06*.test.sh`, `scheduler/feedback-g06.test.sh` and `plugin/skills/node/skill.test.sh`, and the new files' lines in the `Makefile`'s `TESTS`.
**Resolves:** #101

## Purpose
G02 (node-PR updates) and G03 (feedback on the bot's PRs) were built apart, and each is right alone. After this node they also work together on the same node PR. A node's feedback start takes the PR's branch back from a leftover update worktree, as a node's own start does, instead of failing at the checkout until the update runs again. Node feedback waits while an update's question about the same PR is unanswered, so it can neither settle that point nor ask it again. A feedback session's conflicted merge of `main` gets the resolution review that every other conflict resolution gets. An open-PR list cut short at its limit no longer loses a bot PR's pending feedback. A node's feedback already waits while an update of the same PR runs (G03-AC-4: any session of `pr/<N>/`), so this node adds no rule for that.

## Changes
1. **A node's feedback start takes the branch back.** Before it checks the PR's branch out in the node's worktree, a node's feedback start frees the branch from a leftover update worktree (`worktrees/<name>/pr-<N>`) as `start_node` does (`free_branch` over `pr-*`): an idle update worktree holding the branch is detached and the update's own unpushed commits are dropped; one with a running session is not touched, and the feedback waits. A node worktree that an update detached (`node/<ID>/detached` names the branch) goes back on the branch, and the marker is removed. Commits of the node's own that `origin/<branch>` lacks stay on the branch when it is only ahead, and are kept under `refs/noodlebot/leftover/` when they diverged, as G03's start does now. A failure is one status-log line and nothing is handed over. *G06-AC-1.*
2. **Node feedback waits for an update's question.** A node's feedback is held, as for G03's other holds (nothing handed over, the record unchanged), while `pr/<N>/` of its PR holds a node-PR update's `QUESTION.md` without `ANSWER.md`. The held items start their session at the first tick that nothing holds them: after the answer, the answered update runs (G02-AC-2) and the feedback waits for it to end (G03-AC-4). *G06-AC-2.*
3. **A list cut short retires nothing.** The loop's cleanup of pending `FEEDBACK.md` files (a unit whose PR is no longer open) does nothing while the open-PR list is as long as its `--limit`, as G02's `pr_gone` does. The loop passes the limit to `feedback.py`, which in that case removes no record or file of a PR missing from the list. *G06-AC-3, G06-AC-4.*
4. **The resolution review in the node skill's feedback procedure.** The feedback procedure (`--feedback <PR>`) of `plugin/skills/node/SKILL.md` says that a merge of `origin/main` that had conflicts gets the resolution review (G02 change 6) before anything is pushed, with G02's rule for a second rejection: nothing is pushed and the session ends with `QUESTION.md`. The triage skill's feedback procedure never merges `main` and is not changed. *G06-AC-5.*

## Gate
- **G06-AC-1** — After a node-PR update of PR N ended without rc 0 and left its worktree `pr-<N>` on the PR's branch with an unpushed commit of its own, new owner feedback on N starts the node's feedback session on that branch in the node's worktree. The `pr-<N>` worktree is detached and the update's unpushed commit is not on the branch. A node worktree that the update detached is back on the branch with `node/<ID>/detached` removed. A commit of the node's own that `origin/<branch>` lacks is on the branch or under `refs/noodlebot/leftover/`. *Verify:* `scheduler/loop-g06*.test.sh`.
- **G06-AC-2** — While `pr/<N>/` holds a node-PR update's `QUESTION.md` without `ANSWER.md`, new owner feedback on node PR N starts no session, and the unit's `FEEDBACK.md` and the record `feedback/<N>` are unchanged. Once the question is answered and the answered update has ended, the feedback session starts at the next tick that nothing holds it, with every held item in `FEEDBACK.md`. *Verify:* `scheduler/loop-g06*.test.sh`.
- **G06-AC-3** — When the open-PR list has as many lines as its `--limit` and lacks a bot PR whose unit has a pending `FEEDBACK.md` and no running session, that `FEEDBACK.md` stays where it is and no status-log line says it moved. With a shorter list that lacks the PR, it moves into `answered/` as before. *Verify:* `scheduler/loop-g06*.test.sh`.
- **G06-AC-4** — `feedback.py` given an open-PR list as long as the loop's limit keeps the record and `FEEDBACK.md` file of a PR missing from it. Given a shorter list, it removes them. *Verify:* `scheduler/feedback-g06.test.sh`.
- **G06-AC-5** — The feedback procedure of `plugin/skills/node/SKILL.md` requires the resolution review for a merge of `origin/main` that had conflicts, before any push, and on a second rejection pushes nothing and ends with `QUESTION.md`. *Verify:* `plugin/skills/node/skill.test.sh`.

## Risks
- G03 is not merged yet. Its PR may still change `start_feedback`, `fb_blocked` and the node skill's feedback section while it takes in `main` (G02). If its merge already gives one of these criteria (the resolution review in the feedback procedure, say), that criterion's test passes before any change: the PR says so for that criterion instead of showing a RED commit.
- G03-AC-4 holds a node's feedback while any session of `pr/<N>/` runs, which is also where G02's node-PR update of N runs. This node relies on that and has no test of its own for it; if G03 merges without it, the gap comes back.
- An owner who answers an update's question in a comment on the PR, not on the node's home issue (G02-AC-3), makes that comment feedback, and it waits behind the question it answers. The answer belongs on the home issue.
- A held update question holds the node's feedback for as long as the owner leaves it unanswered.
- G04 converts G02's update step and G03's feedback step to the forge interface. Whichever of G04 and this node merges second takes in the other's changes to the same functions of `scheduler/loop.sh` and `scheduler/feedback.py`.
