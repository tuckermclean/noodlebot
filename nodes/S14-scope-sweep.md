# S14 — scope-sweep

| Track | Deps | Unlocks | Size |
|---|---|---|---|

**Owns:** in `scheduler/run-session.sh`: the sweep of a unit's earlier scopes before the probe (Change 1) and its lines in the header comment; in `scheduler/loop.sh`: the `stopped` file of a feedback or triage session killed out of memory (`feedback_ended`, `triage_ended`) and the out-of-memory note (`$oo`) of the background-cut-off end lines of `feedback_ended`, `triage_ended` and `adopt_ended`; in `scheduler/report.py`: the out-of-memory milestone of a spec-PR feedback unit (`post_oom`); in S12's tests `scheduler/run-session-s12.test.sh` and `scheduler/loop-s12.test.sh` and their fakes under `scheduler/testdata/s12/`: only the lines that make each run's unit names its own (Change 5); `scheduler/run-session-s14.test.sh` (new) and `scheduler/loop-s14.test.sh` (new, or `scheduler/loop-s14-*.test.sh` if it is split), their lines in the `Makefile`'s `TESTS`, and any fixtures they add under `scheduler/testdata/s14/`.
**Resolves:** #246

## Purpose
After this node a process a session left in its systemd scope (one that left the process group with `setsid`) no longer holds memory for ever when the loop killed `run-session.sh` itself (`stop_group`, `stop_done`) and the scope was never stopped: with the units on, the next start of the same unit stops and resets every scope its earlier starts left, before the probe, quietly, never failing the start and never touching another unit's scope. Feedback and triage sessions killed out of memory leave the same record as node sessions (their `stopped` file and one milestone on their home issue), every end line of a session killed out of memory names it, the background-cut-off ones included, and S12's tests no longer risk stopping each other's processes when two of their runs start in the same second.

## Changes
1. **The sweep.** With the units on (`SCHED_UNITS=1`, `systemd-run` and `systemctl` found), `run-session.sh` stops and resets, before the probe, every scope an earlier start of its unit left: the scopes named `noodlebot-<runtime name>-<kind>-<key>-<start time>.scope` with this state folder's runtime name, kind and key and any start time (a run of digits), by `systemctl --user stop` and `systemctl --user reset-failed` with that unit name pattern, or with the names `systemctl --user list-units --all` gives for it, kept only when what follows `<key>-` is the start time alone, so that a unit whose key begins with this one's followed by a dash (an adoption area `docs-site` beside `docs`) is never matched. Both calls have their output discarded and their failure ignored: the start goes on to the probe as before. The session's own unit does not exist yet, and the loop never runs two sessions of one state folder at once, so no running session's scope is matched. *S14-AC-1, S14-AC-2.*
2. **A stopped file for feedback and triage.** `feedback_ended` and `triage_ended` call `record_stop` for an end whose `session.unit` holds `oom-kill` and that is neither a `QUESTION.md` end nor a finished rc 0 end (the triage done, the feedback moved to `answered/`), so its `stopped` file names the out-of-memory kill and the ceiling (S12's reason); their other ends write no `stopped` file, as before. *S14-AC-3.*
3. **The milestone of a spec-PR feedback unit.** `report.py`'s `post_oom` no longer skips a spec-PR feedback unit (`PR #<N>` with a `FEEDBACK.md`): its out-of-memory end gets the same one milestone on its home issue (`pr_home`), once per `stopped` file; a spec-PR update unit still gets none. *S14-AC-3.*
4. **The background-cut-off end lines.** The end lines of `feedback_ended`, `triage_ended` and `adopt_ended` for a session whose background work was cut off carry the out-of-memory note (`$oo`) as their other end lines do; without `oom-kill` in `session.unit` the lines read as before. *S14-AC-4.*
5. **Unit names of their own run.** In `scheduler/run-session-s12.test.sh` and `scheduler/loop-s12.test.sh`, every unit name a run makes carries a token of that run alone (for example its scratch folder's name in the repository's runtime name, from which `run-session.sh` builds the unit name), so the fake `systemctl`, which finds a unit's processes by its name across the user's processes, never signals another run's. Only the lines that set the runtime names (and a fake's line, if the token is taken there) change; no check changes what it expects. The PR lists each changed frozen line (file, base line, before and after) for the owner's approval. *S14-AC-5.*
6. The sweep gets its line in `run-session.sh`'s header comment.

## Gate
- **S14-AC-1** — With the units on, a start of `run-session.sh` stops (`systemctl --user stop`) and resets (`systemctl --user reset-failed`) every scope an earlier start of the same unit (runtime name, kind and key) left, before the probe's `systemd-run` call: a child of the earlier first stage that left the process group with `setsid` and outlived a `run-session.sh` killed as `stop_group` kills one is gone before the new first stage starts, and the session then runs and ends as S12-AC-1 says. *Verify:* `scheduler/run-session-s14.test.sh`.
- **S14-AC-2** — The sweep never ends another unit's process (another key, another kind, another runtime name, or an adoption key that begins with this one's followed by a dash) nor stops the start: with the stop or the reset failing, the session runs as without the sweep and the sweep writes nothing to stdout or stderr; with the units off, or `systemd-run` or `systemctl` missing, no `systemctl` call comes before the harness starts. *Verify:* `scheduler/run-session-s14.test.sh`.
- **S14-AC-3** — A triage session, the feedback session of a node PR and the feedback session of a spec PR killed out of memory in their unit each write `stopped` naming the out-of-memory kill and the ceiling, and `report.py` posts one milestone on each one's home issue (the triaged issue; the node's home issue; the spec PR's `pr_home`) naming the kill and the ceiling, and none again on a later run; a `QUESTION.md` end and a finished rc 0 end write no `stopped` file and get no such milestone. *Verify:* `scheduler/loop-s14.test.sh` (with the fake forge).
- **S14-AC-4** — The `status.log` end line of a feedback, a triage and an adoption session whose background work was cut off names the out-of-memory kill and the ceiling when its unit reported `oom-kill`, and the start is not counted, as before. *Verify:* `scheduler/loop-s14.test.sh`.
- **S14-AC-5** — Each run of `scheduler/run-session-s12.test.sh` and `scheduler/loop-s12.test.sh` gives its units names of its own run, so two runs of the same file started in the same second share no unit name; both files pass in `make test`, no check in them changes what it expects, and the PR lists each changed frozen line for the owner's approval. *Verify:* `make test` in CI, and a recorded run of each file twice at once (started together, `taskset` to half the CPUs, each under `timeout`) in which both runs pass and the unit names each logged share none, in the PR.

## Risks
- The sweep runs at the unit's next start only: a session that the loop kills and never starts again (`stop_done` after its PR is merged or closed, a unit held by `FAILED` that the owner never clears) keeps its leftover scope until the unit starts again, the user manager ends, or the owner stops it by hand (`systemctl --user stop 'noodlebot-*.scope'`).
- The pattern rests on S12's unit name (`noodlebot-<runtime name>-<kind>-<key>-<start time>.scope`); a later change to that name must change the sweep with it, which S14-AC-1 then catches.
- Two runtime names whose names, kinds and keys run together into one another's (a runtime name ending in `-node-S01`, say) could still match; the runtime names are the repositories' own, and S14-AC-2 covers the cases that occur (keys with dashes).
- A user manager without the units of an earlier boot has nothing to stop: the sweep is then a no-op, which the failed-call case covers.
- `loop-s14.test.sh` runs several sessions in one loop run; at 10–25 s a case it may need to split into two files to stay under `TEST_FILE_BUDGET` (30 s), each with its own line in `TESTS`.
