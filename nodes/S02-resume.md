# S02 — resume

| Track | Deps | Unlocks | Size |
|---|---|---|---|
| now | T01 | none | M |

**Owns:** the end record (`stopped`), the leftover-changes step and the resume detection in `scheduler/loop.sh`, the resume section of `scheduler/unattended.md`, their cases in `scheduler/loop.test.sh`.
**Resolves:** #18

## Purpose
After this node a node session that ends before its PR without asking anything (the usage limit cuts it off, the owner stops it, it crashes) is started again as a resume, not as a fresh node. The loop records why the session ended, and before the next session starts it saves any uncommitted changes the dead session left as a patch in the node's state and resets the worktree to its last commit, so nothing is committed unexamined. Whenever the node's branch already has commits past `origin/main` or its worktree has `out/node/<ID>/`, the prompt tells the run that it is resuming, why the last one ended, and how to carry on: from its brief, logs, commits and CI runs, without redoing committed and reviewed slices.

## Tests
- `scheduler/loop.test.sh` (extended), in a loop run of its own with its own fixture graph and fake `claude`, so no existing line changes: a node whose first session commits on its branch, writes `out/node/<ID>/brief.md`, leaves a modified tracked file and an untracked file, and ends by the usage limit; one whose session is killed by a signal; one that ends with a non-zero code; a fresh node; a session that ends with a QUESTION.md after an earlier stop; a leftover patch that cannot be written. Each restart's rendered `unattended.md`, `stopped` file, leftover patch, `git status`, HEAD and brief are checked when the next session starts.

## Changes
1. **The loop records why a session ended.** When a node's session ends without a PR, a QUESTION.md or a WAITING-PR, `ended` writes `state/<repo>/node/<ID>/stopped`: one line with the UTC time and the reason, `usage limit` for a limit exit (T01's `limit_exit`), `stopped (signal N)` for an exit code 128+N, `stopped (no exit code)` when there is no `session.rc`, and `rc N` otherwise. A session that ends with a PR, a QUESTION.md or a WAITING-PR removes the file. *S02-AC-1.*
2. **Leftover changes are saved, then reset.** Before `start_node` starts a session in an existing worktree with uncommitted changes (modified, staged, deleted, or untracked and not ignored by Git), the loop writes them to `state/<repo>/node/<ID>/leftover/<UTC timestamp>.patch`, from which `git apply` on the same commit restores every one of them, then resets the worktree to its HEAD and removes the untracked files it saved. Ignored files (`out/` among them) and the branch's commits stay. One status-log event names the node and the patch. If the patch cannot be written, nothing is reset, the node is not started that tick, and the failure is logged. *S02-AC-3.*
3. **The prompt says the run is resuming.** When the node's branch has commits past `origin/main`, or its worktree has `out/node/<ID>/`, the rendered `unattended.md` carries a resume section: the reason from `stopped` (if any), the number of commits past `origin/main`, the leftover patch (if one was written for this start), and what to do: read `out/node/<ID>/` (brief, logs) and `git log origin/main..HEAD`; keep the existing brief and add to it rather than rewrite it; carry on from the last reviewed slice and never redo a committed and reviewed one; list the CI runs on the branch (`gh run list --branch`) and wait for or read any the earlier session started before starting a new one; examine the leftover patch, never apply or commit it unexamined, and list it in the PR under Deviations with what was done with it. A node with none of these gets no resume section. The existing resume after an answered question (`answered/`) stays. *S02-AC-2.*
4. **End to end.** The limit-stopped and signal-stopped cases of `loop.test.sh` show the whole path: the stop record, the saved and reset worktree, the untouched commits and brief, and the resume prompt. *S02-AC-4.*

## Gate
- **S02-AC-1** — When a node's session ends without a PR, a QUESTION.md or a WAITING-PR, `state/<repo>/node/<ID>/stopped` holds one line with the UTC time and the reason: `usage limit` for a limit exit, `stopped (signal N)` for an exit code 128+N, `stopped (no exit code)` with no `session.rc`, `rc N` otherwise; when a later session of the node ends with a PR, a QUESTION.md or a WAITING-PR, the file is gone. *Verify:* `scheduler/loop.test.sh`.
- **S02-AC-2** — A node started while its branch has commits past `origin/main`, or while its worktree has `out/node/<ID>/`, gets a rendered `unattended.md` with a resume section that gives the reason from `stopped`, the number of commits past `origin/main` and the leftover patch written for this start (if any), and tells the run to read `out/node/<ID>/` and `git log origin/main..HEAD`, keep the existing brief, not redo committed and reviewed slices, look up the branch's CI runs (`gh run list --branch`) before starting a new one, and examine the leftover patch, never commit it unexamined, and list it under Deviations in the PR. A node started with neither gets no resume section. *Verify:* `scheduler/loop.test.sh` (the rendered prompt).
- **S02-AC-3** — When a node starts in a worktree with uncommitted changes, those changes (modified, staged, deleted and untracked files Git does not ignore) are in `state/<repo>/node/<ID>/leftover/<UTC timestamp>.patch`, which `git apply` on the same commit turns back into them; when the session starts, `git status --porcelain` in the worktree is empty, HEAD and the branch are unchanged, ignored files (`out/node/<ID>/` among them) are untouched, and one status-log event names the node and the patch. A clean worktree gets no patch. When the patch cannot be written, the worktree is unchanged, the node does not start that tick, and the failure is logged. *Verify:* `scheduler/loop.test.sh`.
- **S02-AC-4** — A node whose first session commits on its branch, writes `out/node/<ID>/brief.md`, leaves an uncommitted edit and ends by the usage limit starts again (with its start not counted, as T01 does) with the resume prompt naming `usage limit`; at that start its earlier commits are on the branch with HEAD unchanged, its brief is unchanged, and the edit is in the leftover patch, not in the worktree. A node whose session is killed by a signal restarts the same way, with a reason beginning `stopped`. *Verify:* `scheduler/loop.test.sh`.

## Risks
- The dead session's conversation is lost: the resume rests on the brief, the logs and the commits. A slice reviewed but not yet recorded in `out/node/<ID>/` is reviewed again.
- How a hand stop shows up depends on what was killed: the `claude` process gives `run-session.sh` an exit code of 128+N, while killing `run-session.sh` itself leaves no `session.rc` (unverified for real sessions). Both are read as a stop.
- A hand stop or a crash still uses a start, as before this node; two in a row write FAILED. Only limit exits give their start back (T01).
- Whether a run actually follows the resume section (keeps its brief, picks up a CI run) is session behaviour the end-to-end test with fakes cannot show; the test shows the prompt it gets.
- Triage sessions are not covered: a restarted triage still gets its usual prompt.
- Other restarts of a node with a kept worktree, such as S01's release of a closed PR's node once its FAILED is deleted, get the same resume prompt and leftover step.
