# S03 — merged-followup

**Owns:** the merged-node follow-up in `scheduler/ready.py`; the follow-up start (branch, worktree, prompt), the follow-up cases of the merged-PR stop (`pr_done`), of the "ended with a PR" check (`ended`) and of the merged-worktree cleanup (`cleanup_merged`) in `scheduler/loop.sh`; the follow-up prompt `scheduler/unattended-followup.md`; the answered and merged-question items of `scheduler/report.py`'s "Waiting on you" section and its reply to an answer; their cases in `scheduler/ready.test.sh`, `scheduler/loop.test.sh` and `scheduler/report.test.sh`.
**Resolves:** #31

## Purpose
After this node an owner's answer to a node whose PR is already merged is acted on. When such a node's QUESTION.md is answered (or the spec PR its WAITING-PR names is merged), the loop starts a follow-up session for it on a new branch `node/<ID>-followup-<n>` made from `main`, whose prompt says that the node's PR is merged, that the answer is carried out as a follow-up PR (or a spec PR, as usual), and where the last run left its brief, logs and set-aside branches. The follow-up runs, counts its starts and ends like any session, and is stopped only for its own PR, not for the node's earlier merged one. The status issue no longer promises that an answer "resumes within seconds" when nothing will start it: it says so only when `ready.py` would start the node, and otherwise says what the answer waits for; a merged node's open question is shown as one whose answer starts a follow-up.

## Tests
- `scheduler/ready.test.sh` (extended): a merged node (by `--merged` and by squash subject) with an answered question; with a WAITING-PR whose PR is in `--merged-prs`; with a FOLLOWUP marker, with and without `--open`; with no markers; with an unanswered QUESTION.md; with FAILED; with a WAITING-PR not yet merged; unmerged nodes printed as before.
- `scheduler/loop.test.sh` (extended): the fake `gh` lists a node's PR as merged while its QUESTION.md is answered. Cases: the follow-up starts on `node/<ID>-followup-1` from `origin/main` in its own worktree, with the follow-up prompt; a second follow-up after the first one's PR merged takes `-followup-2`; the follow-up session is not stopped while the node's original PR stays merged, and is stopped when its own PR is merged or closed; a follow-up that ends without a PR on its branch uses a start, and the second such end writes FAILED; a follow-up that asks a question and is answered resumes on the same branch and worktree; a merged node with no markers or an unanswered question starts nothing.
- `scheduler/report.test.sh` (extended): the "Waiting on you" item and the reply to an answer for an answered node that `ready.py` would start (unmerged and merged), for one it would not (FAILED, a WAITING-PR not yet merged, a dep not merged, a node missing from the graph), and the item for a merged node's unanswered question.

## Changes
1. **`ready.py` names a merged node with an answer to act on.** A merged node whose markers say resume (QUESTION.md with ANSWER.md, or a WAITING-PR whose number is in `--merged-prs`, and no FAILED) is printed in graph order with the other ready nodes, with a third word `followup` on its line. So is a merged node with a FOLLOWUP marker (the loop's record of a follow-up in progress) that an unmerged node in its place would be ready as: no FAILED, no unanswered QUESTION.md, no WAITING-PR not yet merged, and no open PR (`--open`). A merged node with no markers, an unanswered QUESTION.md, FAILED or a WAITING-PR not yet merged is not printed. Lines for unmerged nodes are unchanged. *S03-AC-1.*
2. **The loop starts a follow-up.** For a `followup` line, `start_node`'s path releases the markers into `answered/` and resets the starts to 0 as for any answer, then creates a worktree of its own on a new branch `node/<ID>-followup-<n>` from `origin/main`, where `<n>` is one more than the highest follow-up number of that node among the clone's branches, origin's branches and the merged and closed PRs (1 when there is none), writes the session prompt from `scheduler/unattended-followup.md`, and starts the session. A FOLLOWUP marker in the node's state folder holds the current follow-up branch; while it is there, a later start reuses that branch and its worktree. One status-log event names the node, the follow-up branch and the start count. *S03-AC-2, S03-AC-3.*
3. **The follow-up prompt.** `scheduler/unattended-followup.md` carries the rules of `scheduler/unattended.md` (questions, spec PRs and WAITING-PR, GitHub access, closing keywords, when to end) and says in addition: the node's PR is merged; the answers in `answered/` are carried out as a follow-up PR from this branch (or a spec PR, as usual); the last run's brief and logs are archived under `state/archive/<ID>-out`, the node's earlier branch and any branches the last run set aside are local branches of the clone (`git branch` in the worktree lists them), and its QUESTION.md and ANSWER.md files are in `answered/`. *S03-AC-3.*
4. **A follow-up is stopped only for its own PR.** `pr_done` does not take the node's earlier merged PR as a reason to stop a follow-up session; it stops it, as S01 does for any node, when a PR on the current follow-up branch is merged, or is closed without merging after the session started while no PR of the node is open. When a PR on the current follow-up branch is merged, the loop moves the FOLLOWUP marker into `answered/` (running session or not), so the follow-up is done. *S03-AC-4, S03-AC-6.*
5. **A follow-up ends like any session.** In `ended`, a follow-up counts as ended with a PR only when its current follow-up branch has an open or merged PR; otherwise, without QUESTION.md or WAITING-PR, its start is used, and the second such end writes FAILED, as for any node. *S03-AC-5.*
6. **A pending follow-up keeps its branch and worktree.** An answer to a question a follow-up asked (or its merged WAITING-PR) resumes that follow-up on its branch and worktree rather than starting a new number. `cleanup_merged` leaves a follow-up's worktree in place while its FOLLOWUP marker is there, and archives its evidence and removes it as for any merged node once the marker is gone. *S03-AC-6.*
7. **The status issue says what an answer waits for.** In "Waiting on you", a merged node with an unanswered QUESTION.md reads "<ID>'s PR is merged; its question is still open, and an answer starts a follow-up". An answered node, and the reply recording an answer, say it resumes within seconds (a follow-up starts within seconds, for a merged node) only when `ready.py`, run on the loop's latest inputs in the state folder (`graph.yaml`, `subjects.txt`, `merged-prs.txt`, the merged node IDs from `merged-prs.tsv`), names that node; otherwise they say what it waits for: its FAILED marker (with its reason), the unmerged spec PR of its WAITING-PR, its unmerged deps, or that it is not in the graph. When `ready.py` cannot be run, they say the answer is recorded and claim no timing. *S03-AC-7, S03-AC-8.*

## Gate
- **S03-AC-1** — `ready.py` prints a merged node (merged by `--merged` or by its squash subject) whose QUESTION.md has an ANSWER.md, or whose WAITING-PR number is in `--merged-prs`, as `<ID> <name> followup`, in graph order among the ready nodes, and prints the same for a merged node with a FOLLOWUP marker, no FAILED, no unanswered QUESTION.md, no WAITING-PR outside `--merged-prs` and no `--open`; it does not print a merged node that has no markers, an unanswered QUESTION.md, FAILED, or a WAITING-PR not in `--merged-prs`; its lines for unmerged nodes are exactly as before. *Verify:* `scheduler/ready.test.sh`.
- **S03-AC-2** — At the first tick after a merged node's question is answered, the loop moves QUESTION.md and ANSWER.md into `answered/`, and starts one session, as start 1 of 2, in a new worktree on branch `node/<ID>-followup-1` whose first commit is `origin/main`'s head; one status-log event names the node and that branch. When the node already had a follow-up whose PR is merged, the next answered question starts `node/<ID>-followup-2`. A merged node with no markers or an unanswered QUESTION.md starts no session. *Verify:* `scheduler/loop.test.sh`.
- **S03-AC-3** — The follow-up session's appended prompt (its `unattended.md` in the node's state folder) says that the node's PR is merged, that the answer is to be carried out as a follow-up PR from its branch or as a spec PR with WAITING-PR, and names the node's `answered/` folder, `state/archive/<ID>-out`, and the clone's local branches as where the last run left its work; it keeps `scheduler/unattended.md`'s rules for QUESTION.md, WAITING-PR, GitHub access and closing keywords. *Verify:* `scheduler/loop.test.sh`.
- **S03-AC-4** — A running follow-up session is not stopped while the node's earlier PR stays merged and its follow-up branch has no merged or closed PR; it is stopped within a tick, with one status-log event naming the PR, when a PR on its follow-up branch is merged, or closed without merging after the session started (then held by FAILED, as S01-AC-2 says). *Verify:* `scheduler/loop.test.sh`.
- **S03-AC-5** — A follow-up session that ends with no open or merged PR on its follow-up branch, no QUESTION.md and no WAITING-PR is not logged as ended with a PR: its first such end starts it again at the next tick on the same branch, as start 2 of 2, and its second writes FAILED with starts 0, as for any node; while its follow-up PR is open it does not start again. *Verify:* `scheduler/loop.test.sh`.
- **S03-AC-6** — When a follow-up session ends with QUESTION.md, its worktree and branch stay; after the answer, the next session runs on the same follow-up branch and worktree, with its earlier commits, and no new follow-up number is taken. Once the follow-up's PR is merged, its FOLLOWUP marker is moved into `answered/`, the node starts no session at later ticks, and, once no session runs, its evidence is archived under `state/archive/` and its worktree removed. *Verify:* `scheduler/loop.test.sh`.
- **S03-AC-7** — For a merged node with an unanswered QUESTION.md, the status issue's "Waiting on you" item says that the node's PR is merged, its question is still open, and an answer starts a follow-up; the question is posted, and an answer to it is recorded, as for any node. *Verify:* `scheduler/report.test.sh`.
- **S03-AC-8** — The "Waiting on you" item for an answered question and the reply recording an answer say "resumes within seconds" (or that a follow-up starts within seconds, for a merged node) only when `ready.py` on the state folder's latest inputs names that node; for a node held by FAILED, a WAITING-PR not in the merged PRs, an unmerged dep, or absence from the graph, they say that instead, and neither says "within seconds". *Verify:* `scheduler/report.test.sh`.

## Risks
- The follow-up session runs `/noodlebot:node <ID>` (or the repository's `/node`) on a node that is already merged; the skill is written for unmerged nodes, and only the appended prompt steers it to a follow-up PR. How a real session takes that is unverified until the first live follow-up; the loop test uses fake sessions.
- On deploy, an answered question of a merged node already waiting in another repository's state (themonolith's R05, answered 2026-11-09) starts its follow-up at the next tick, with that answer's QUESTION.md (Q5, Q6) as its brief.
- "Resumes within seconds" is still said while the throttle holds new sessions or `SCHED_MAX` is reached: `ready.py` knows neither, and issue #31 asks only for its verdict.
- `scheduler/status.sh` and `scheduler/loops.sh` keep their own wording; an answered merged node is listed as answered only until the next tick starts its follow-up.
- A follow-up PR's squash subject also starts with `<ID> <name>:`; the node is merged already, so nothing changes in `ready.py`'s view, but a follow-up's own merge is recognised only through its PR on `node/<ID>-followup-<n>` (500-PR list limit, as for the other PR lists).
- `scheduler/loop.sh`'s `ended` and stop paths are also changed by S02; whichever merges later resolves the conflict.
