**Resolves:** #35

## Purpose
After this node GitHub shows which version of noodlebot wrote something. The version is `git describe --tags --always` of the live checkout, printed by `scheduler/version.sh` and taken once per loop start. Because a deploy re-execs the loop (D01), that means once per deploy. Every comment and issue body `report.py` writes, and every PR body and comment a session writes, ends with a signature naming that version and linking its commit. Commits made in a session carry a `Noodlebot-Version:` trailer. Locally, the status log, the status issue header, `status.sh` and `loops.sh status` show the version. Whether and when to cut release tags is the owner's choice and not part of this node: until a tag exists, the version is the short commit.

## Changes
1. **`scheduler/version.sh [<checkout>]`.** Prints `git describe --tags --always` of the given checkout (by default the one it lives in): for example `v0.4.0` on a tag, `v0.4.0-3-g4458b14` after it, or `4458b14` while there are no tags. Outside a Git checkout it prints `unknown`. Either way it exits 0. `--signature` prints the signature line `— n00dl3b0t [<version>](https://github.com/<owner/name>/commit/<full sha>)`, where `<owner/name>` is taken from the checkout's `origin` URL (HTTPS or SSH form, never a fixed name). With no GitHub `origin`, the line is `— n00dl3b0t <version>` with no link. *V01-AC-1, V01-AC-2.*
2. **The loop takes the version once per start.** At its start, before the label step, `loop.sh` runs `version.sh` and `version.sh --signature` on its own checkout and keeps both for the whole run. It writes the version to `state/<name>/version` and one status-log line `loop started for <owner/name>, version <version>`. A re-exec after a deploy is a new start, so the line is written again with the new version. *V01-AC-3.*
3. **Deploy events name versions.** `deploy.sh` adds `git describe --tags --always` of the commits to its event lines: `deployed <old>..<new> (version <new version>)`, `not deployed: <sha> (version <version>) …`, and `rolled back <cur>..<prev> (version <prev version>)`. *V01-AC-4.*
4. **Session prompts carry the version.** Every `scheduler/unattended*.md` template has a `@VERSION@` placeholder (and the signature line, as a placeholder or built from `@VERSION@`), rendered by the loop like `@STATE@`. Each template tells the session to end every PR body and every comment it writes on GitHub with the signature line, including what it posts for its subagents (a fresh review, a triage comment, a spec or node PR body). `run-session.sh` passes the version to the session's environment as `NOODLEBOT_VERSION`. *V01-AC-5.*
5. **Commits made in a session carry the trailer.** At start the loop installs a `commit-msg` hook in its clone (`repos/<name>`), shared by every worktree of that clone. When `NOODLEBOT_VERSION` is set, the hook adds `Noodlebot-Version: <version>` to the message (`git interpret-trailers`, one trailer, kept if one is already there). When it is not set, the hook does nothing. *V01-AC-6.*
6. **`report.py` signs what it writes.** `report.py --version <version> --signature <line>` (passed by the loop) ends every comment it posts and the issue body with the signature line, after any cut of an over-long comment, and names the version in the body's header. Without those options it writes as before. *V01-AC-7.*
7. **Local views.** `status.sh` prints `version: <version>` from `state/<name>/version` while the loop runs. `loops.sh status` adds `version <version>` to each running loop's line. *V01-AC-8.*

## Gate
- **V01-AC-1** — `scheduler/version.sh <checkout>` prints `git describe --tags --always` of that checkout: the tag on a tagged commit, `<tag>-<n>-g<short sha>` on a later commit, the short commit when there is no tag. Outside a Git checkout it prints `unknown`. It exits 0 in every case. *Verify:* `scheduler/version.test.sh`.
- **V01-AC-2** — `scheduler/version.sh --signature <checkout>` prints `— n00dl3b0t [<version>](https://github.com/<owner/name>/commit/<full sha of HEAD>)`, with `<owner/name>` taken from the checkout's `origin` URL in its HTTPS and SSH forms. With a non-GitHub `origin` or no `origin` it prints `— n00dl3b0t <version>`. *Verify:* `scheduler/version.test.sh`.
- **V01-AC-3** — Each loop start, including the start a deploy's re-exec makes, writes exactly one status-log line `loop started for <owner/name>, version <version>` and writes that version to `state/<name>/version`. After a deploy, the new line names the deployed commit's version. *Verify:* `scheduler/loop.test.sh`.
- **V01-AC-4** — Each status-log event of a deploy, a commit not deployed and a rollback names the version (`git describe --tags --always`) of the commit it deploys, refuses or returns to. *Verify:* `scheduler/deploy.test.sh` (the lines) and `scheduler/loop.test.sh` (in the status log).
- **V01-AC-5** — Every `scheduler/unattended*.md` template contains `@VERSION@`. The node and triage prompts the loop renders contain no `@VERSION@`. They contain the loop's version and its signature line, and they tell the session to end every PR body and comment it writes on GitHub with that line. A session started by `run-session.sh` has `NOODLEBOT_VERSION` set to that version in its environment. *Verify:* `scheduler/loop.test.sh`.
- **V01-AC-6** — A commit made during a session, in its worktree or in another worktree of the same clone, ends with exactly one trailer `Noodlebot-Version: <the version the session was started with>`. This holds whether or not the session wrote one itself. A commit made in the clone outside any session gets no such trailer. *Verify:* `scheduler/loop.test.sh`.
- **V01-AC-7** — With a version given by the loop, every comment `report.py` posts (events, questions, answer replies, "not recorded" replies, an over-long comment after its cut) and the status issue body end with the signature line, and the body's header names the version. With none given, `report.py` writes as before. *Verify:* `scheduler/report.test.sh`.
- **V01-AC-8** — While a loop runs, `status.sh <owner/name>` prints `version: <version>` and `loops.sh status` names that version on the repository's line. Both read it from `state/<name>/version`. *Verify:* `scheduler/version.test.sh` (`status.sh`) and `scheduler/loops.test.sh`.

## Risks
- PR bodies and comments written by sessions are signed only because the prompt says so. A session or subagent that ignores it leaves an unsigned PR or comment. Only `report.py`'s output and the commit trailer are enforced by code.
- A repository that sets `core.hooksPath` in its clone's configuration, or a session that commits with `--no-verify`, bypasses the trailer hook.
- A session started before a deploy keeps the version it started with (prompt and trailer), while the loop and `report.py` already show the new one. This is correct, since the session runs the skills it loaded, but two versions can appear on one PR.
- The node PR is squash-merged, so the trailers on its branch commits reach `main` only as far as the squash message keeps them.
- Open spec PR #38 (U01, U02) moves `report.py`'s comments to unit and daily issues. Whichever node is built second carries the signature to the comments and bodies that exist by then. V01-AC-7 covers every comment `report.py` posts, not one issue.
- The bot's name `n00dl3b0t` in the signature is the GitHub App's. Another installation under a different App name would show the wrong name.
