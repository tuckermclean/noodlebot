**Resolves:** #103

## Purpose
After this node a spec PR changes only the repository's spec files, so no code or test reaches `main` without the test-first build, the fresh review and the criterion → evidence table a node PR gives it. The node skill and the session templates state one rule instead of two that contradict each other: the owner's approval of a frozen test line or of a file outside the node's Owns is recorded in the answer, and the change is made on the node branch. A checker stops a spec branch that touches anything else before it is pushed. The loop sends a node whose open spec PR touches other files back to move them out, a spec PR closed without merging releases its node instead of holding it forever, and files that already reached `main` through a merged spec PR are reviewed in the node's PR.

## Changes
1. **The checker.** `plugin/skills/node/check-spec-diff.py [--repo <dir>] [--allow <path>]... <from> <to>` judges `git diff --name-only --no-renames <from>...<to>`. The spec files are the paths in backticks on the `**Spec files:**` line of `AGENTS.md` (its "Building a node" section) as it is at `<from>`, so a branch cannot widen its own list; a path ending in `/` is a folder. With no such line they are `SPEC.md`, `docs/graph.yaml` and `nodes/`. `--allow` adds a path for one run. It prints the list it used and where it came from, then one line `NOT SPEC <path>` per changed path outside it. It exits 0 when there is none, 1 when there is one or more, and 2 when git fails, with nothing on stdout. It names no repository. This repository's `AGENTS.md` gets the line: `SPEC.md`, `docs/graph.yaml`, `nodes/`. *G05-AC-1.*
2. **One rule in the node skill and both node templates.** Step 7 of `plugin/skills/node/SKILL.md`, and the SMALL SPEC AMENDMENTS and SPEC CHANGES rules of `scheduler/unattended.md` and `scheduler/unattended-followup.md`, say the same:
   - a spec PR changes only the repository's spec files (the checker's list);
   - changing a frozen test line, or a file outside the node's **Owns:**, needs the owner's approval asked for as a question, and the approval is recorded in the answer (and quoted in the spec PR when there is one);
   - the change itself is made on the node branch, test-first, where the node's review and evidence table cover it;
   - adding a path to the node's own **Owns:** stays a small amendment in the node PR;
   - before pushing a spec branch the session runs the checker against `origin/main` and, on exit 1, removes those changes from the spec branch, and stops if it cannot.
   The templates name no repository's spec files themselves; they point to the checker. *G05-AC-2, G05-AC-3.*
3. **Files a merged spec PR carried are reviewed in the node's PR.** When the node's `answered/` names merged spec PRs (`<ts>-SPEC-PR`), the session runs the checker on each PR's merge commit (`<sha>^ <sha>`). Every file outside the spec files that it changed gets a row in the node PR's criterion → evidence table, naming the spec PR, and the whole-node fresh reviewer gets those diffs and reviews them as part of the node. *G05-AC-2.*
4. **The triage and adopt skills follow the rule.** `/noodlebot:triage` (section 3) and `/noodlebot:adopt` run the checker against `origin/main` before they push and stop on exit 1. Adopt runs it with `--allow AGENTS.md`, and the "Building a node" section it drafts has a **Spec files:** line. *G05-AC-4.*
5. **A spec PR closed without merging releases its node.** `ready.py --closed-prs <file>` (the numbers of PRs closed without merging, from the loop's `closed-prs.tsv`) treats a WAITING-PR whose number is in it as a resume, as a merged one is. `release-markers.sh` moves it into `answered/<ts>-SPEC-PR-CLOSED` and prints `spec PR #N closed without merging`. The templates say that its spec changes did not land, that the approvals in `answered/` that need no spec change are carried out on the node branch test-first, and that a spec change still needed is a new question, not a reopened PR. *G05-AC-5.*
6. **The loop sends out-of-scope spec PRs back.** Each tick, for each node whose WAITING-PR names an open PR, the loop runs the checker on the clone (`origin/main` against `origin/<branch>`) once per head commit. When it exits 1 and `AGENTS.md` on `origin/main` has a **Spec files:** line, the loop writes `SPEC-PR-SCOPE` next to WAITING-PR: the PR's number, branch, head commit and the paths outside the spec files. `ready.py` treats it as a resume, `release-markers.sh` moves it into `answered/<ts>-SPEC-PR-SCOPE` and removes WAITING-PR, and the start is one status-log event naming the PR and its paths. When the line is missing the loop starts nothing and logs one line per head commit saying the repository names no spec files. When the head a later session waits on is still out of scope, the loop writes FAILED naming the PR and the paths. *G05-AC-6.*
7. **What the sent-back session does.** The templates' RESUMING section says, for `<ts>-SPEC-PR-SCOPE`: on the spec branch (a worktree at `origin/<branch>`), one new commit puts each listed path back to its `origin/main` state, with no amend, rebase or force push. The session runs the checker (exit 0) and the spec checker (PROBLEMS 0), and comments on the PR with the paths taken out and the commit that held them. A PR with no change left against `origin/main` is closed with that comment, and the node carries on, making the approved changes on its branch test-first. Otherwise the session writes WAITING-PR again with the same number and ends, and makes the approved changes after the merge. Either way the PR body or comment and the node's brief name the removed paths, so the resumed session makes them. *G05-AC-7, G05-AC-8.*

## Risks
- The sessions follow the rule by reading it. The checker and the loop's scope check catch a session that does not, but only for spec PRs a node waits on (WAITING-PR). A triage or adopt spec PR is checked only by its own session.
- A repository whose `AGENTS.md` has no **Spec files:** line gets no repair from the loop, and its sessions check against the default list. A spec file outside that list (themonolith's `docs/migration.tsv`) then stops a session that touches it. The repair of themonolith's spec PRs #87 and #83 and the review of #84's test changes (issue #103) happen only once themonolith's `AGENTS.md` names its spec files, after this node is deployed.
- Restoring paths to `origin/main` is a commit on the PR's branch, not a revert of the earlier commit. A path `main` changed since the spec PR branched is put back to `main`'s current state, which is what the PR then shows.
- Closing a PR is a forge write the bot has not made before. It only ever closes its own spec PR, and only one with no change left.
- Until the node's start releases it, a WAITING-PR whose PR is closed still reads "waits for you to merge spec PR #N" in the status texts (U03 changes those texts for a merged one only).
- The evidence rows for files a merged spec PR carried depend on the session finding each PR's merge commit. A spec PR merged before this node, whose `<ts>-SPEC-PR` is no longer in `answered/`, is not found.
