## Purpose
After this node the loops keep the machine's disk in hand on their own, so the owner no longer prunes podman images and stale build folders by hand when the disk fills. With `~/.config/noodlebot/housekeeping` present, one loop of the machine, at most once a day and only while no podman or buildah process runs, prunes the images no container uses and removes the user's `/var/tmp/buildah*` folders older than a day. Every tick each loop reads the free disk of the runtime root's filesystem, the status issue shows it, and below a threshold no new session starts, with the reason, as while the throttle holds. Without the file nothing changes. Nothing in it names one repository or one image.

## Changes
1. **The disk check.** `disk.py check --state-root DIR` runs `df -Pk` on the runtime root (the parent of `DIR`), writes `DIR/disk.json` (path, size, free, threshold, hold, reason, time) by writing a new file and renaming it over the old, and prints `open: <free> free` or `hold: <free> free on <path>, below <threshold>`. The threshold is `SCHED_DISK_MIN_GB` (default 5, in GB; 0 turns the hold off and still records the free space). A `df` that fails or cannot be read is one stderr line, a non-zero exit and a `disk.json` with the free space unknown and no hold. *M06-AC-1.*
2. **The housekeeping run.** `disk.py housekeep --state-root DIR` takes `DIR/housekeeping.lock` without waiting (another run holding it: exit 0, nothing printed); does nothing when the last recorded run started less than `SCHED_HOUSEKEEP_EVERY` seconds ago (default 86400); and, right before each step, looks for a process whose command name is `podman` or `buildah` (in `/proc`, or the folder `--proc` names): with one, it prints one line naming it, records nothing as the day's run, and stops. Otherwise it runs, in order:
   - `podman image prune --all --force`, which removes only images no container (running or stopped) uses; without `podman` on `PATH`, one line and the step is skipped; a failure is named and the next step still runs;
   - every directory (not a symbolic link) matching `buildah*` directly in the build folder (`SCHED_BUILD_TMP`, default `/var/tmp`), owned by the user and last modified more than a day ago, is removed with `rm -rf`, and when it is still there with `podman unshare rm -rf`; one that remains is named as failed and the others are still removed.
   It touches no container, volume or other file, never runs `podman system prune`, and records `DIR/housekeeping.json` (start, end, images removed, folders removed and failed, free space before and after) the same way as `disk.json`. It prints one summary line. *M06-AC-2, M06-AC-3.*
3. **The loop holds below the threshold.** With `~/.config/noodlebot/housekeeping` present (read each tick), each tick runs `disk.py check` before the throttle's decision. While it says hold, the loop treats starts as while the throttle holds, whether or not the throttle is on: no node, triage, update, feedback, adoption or follow-up session starts, no idle session is resumed, the start queue does not ask for a turn, and a `RELEASE` marker starts its node as it does under the throttle. Running sessions go on. Engaging and releasing are one status-log line each, the engaging line with the hold's reason. A check that fails is one status-log line (not repeated while it keeps failing) and holds nothing. *M06-AC-4, M06-AC-5.*
4. **The loop starts housekeeping.** With the file present, each tick starts `disk.py housekeep` in the background (with the loop's lock closed, as a session's start does) unless the one it started last is still running; the tick does not wait for it. When it has ended, its summary or waiting line, when it printed one, is one status-log line starting `housekeeping:`; a waiting line is not repeated until it changes. *M06-AC-5.*
5. **Without the file nothing changes.** No `disk.py` runs, no `disk.json` or `housekeeping.json` is written, no `podman` is called and the free space holds nothing. `loops.sh start` already passes the `SCHED_*` settings to every loop, and `deploy.sh`'s `make test` runs without them. *M06-AC-6.*
6. **The status issue.** `report.py` adds a Disk line to the status table from `disk.json` when it exists: the free space, the size and the path; "**holding new sessions**: <reason>" while it holds; and from `housekeeping.json` the last run's local time, the space it freed and, when any, the count of folders it could not remove. The start clause of a waiting unit names the disk hold with its reason, as it names the throttle's. The disk hold's engaging and releasing lines and the `housekeeping:` lines are event comments of the day's log issue. With no `disk.json`, the body is unchanged. *M06-AC-7.*
7. **The README** gets the `housekeeping` row in its table of files under `~/.config/noodlebot/` and the settings `SCHED_DISK_MIN_GB`, `SCHED_HOUSEKEEP_EVERY` and `SCHED_BUILD_TMP`.

## Risks
- The check reads the filesystem of the runtime root only. Podman's storage (`~/.local/share/containers`) and `/var/tmp` are on it on this machine (`/`, 89% used and 8 GB free on 2026-11-27); where they lie on another filesystem, the hold does not see that one.
- An image a session pulled and has not run yet is pruned when housekeeping runs between the pull and the run, and is pulled again; the check for podman processes makes this rare, not impossible. Images the repositories pull by digest come back the same.
- A folder owned by another user is left by rule, and the user's own folders owned by subordinate ids inside need `podman unshare`; an unprivileged test cannot make a folder of another owner, so the owner check is shown by the code and the review, not a test.
- The default threshold, 5 GB, is a guess at what a session needs (a worktree and a container build); the owner sets `SCHED_DISK_MIN_GB` for the machine. A hold that never releases because nothing frees space shows on the status issue with its reason; the owner frees space or lowers the threshold.
- A loop started before this node is deployed runs the old loop until its re-exec; the file does nothing until then.
