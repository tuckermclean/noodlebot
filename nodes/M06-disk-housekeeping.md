## Purpose
After this node the loops keep the machine's disk in hand on their own, so the owner no longer prunes podman images and stale build folders by hand when the disk fills. With `~/.config/noodlebot/housekeeping` present, one loop of the machine, at most once a day (and once more when the disk hold engages), removes the dangling podman images and the unused images that can be pulled back, keeps every image built on the machine, and removes the user's `/var/tmp/buildah*` folders older than a day; the image step runs only while no session runs under the runtime root and no podman or buildah process runs, the folder step only while no podman or buildah process runs, so housekeeping never disturbs a running session. Every tick each loop reads the free disk of the runtime root's filesystem, the status issue shows it, and below a threshold no new session starts, with the reason, as while the throttle holds. Without the file nothing changes. Nothing in it names one repository or one image.

## Changes
1. **The disk check.** `disk.py check --state-root DIR [--now EPOCH] [--df-timeout S]` runs `df -Pk` on the runtime root (the parent of `DIR`) with a timeout of `--df-timeout` seconds (default 30), writes `DIR/disk.json` (path, size, free, threshold, hold, reason, time, and while it holds the time the hold engaged, kept from the last record while it goes on holding) by writing a new file and renaming it over the old, and prints `open: <free> free` or `hold: <free> free on <path>, below <threshold>`. The time is `--now` when given, otherwise the clock. The threshold is `SCHED_DISK_MIN_GB` (default 5), in GB of 10^9 bytes: it holds when the free bytes (the KiB `df` reports × 1024) are below `SCHED_DISK_MIN_GB` × 10^9; 0 turns the hold off and still records the free space. A `df` that fails, outlasts the timeout or cannot be read is one stderr line, a non-zero exit and a `disk.json` with the free space unknown and no hold. *M06-AC-1.*
2. **The housekeeping run.** `disk.py housekeep --state-root DIR [--now EPOCH]` takes `DIR/housekeeping.lock` without waiting (another run holding it: exit 0, nothing printed). It is due when the last complete run started `SCHED_HOUSEKEEP_EVERY` seconds (default 86400) or more before now (`--now`, or the clock), or when `disk.json` holds and the hold engaged after the last complete run's start (so a hold brings one run forward, once per hold); otherwise it does nothing. Right before each step it looks for a process whose command name is `podman` or `buildah` (in `/proc`, or the folder `--proc` names): with one, it prints one line naming it and stops. Otherwise it runs, in order:
   - the image step, only when no session runs under the runtime root (the count of running sessions S13 adds to `turn.py`, as its machine budget counts them, read with `turn.py`, not a copy of its own); with sessions running, one line naming how many, and the step waits for a later run. It calls `podman image prune --force` (dangling images, which no name points at), then `podman images --format json`, and for each image it reports with no containers (running or stopped), `podman rmi <id>` (no `--force`) when one of its `RepoDigests` names a registry other than `localhost/`; the session count is read again before each `rmi`, and a session that appears ends the step. An `rmi` that refuses (the image is in use, or podman wants `--force`) is a skip, recorded with its reason, not a failure. Every other unused image (tagged, with only `localhost/` digests or none, so built here and not to be pulled back) is kept and recorded as kept. Without `podman` on `PATH`, one line and the step is skipped; a failure is named and the next step still runs;
   - the folder step: every directory (not a symbolic link) matching `buildah*` directly in the build folder (`SCHED_BUILD_TMP`; unset, empty or a relative path means `/var/tmp`), owned by the user and last modified more than a day before now, is removed with `rm -rf`, and when it is still there with `podman unshare rm -rf`; one that remains is named as failed and the others are still removed.
   It touches no container, volume or other file, never runs `podman system prune`, and records `DIR/housekeeping.json` the same way as `disk.json`: start, end, the build folder, each removed image (id, names, digests), each kept or skipped image (id, names, size, and why), each removed and each failed folder path, the free space before and after, and whether the run is complete. A run is complete, and counts as the period's run, only when both steps ran; a run that stops or waits, before a step or after one, still writes the record with what it removed (nothing, when it stopped before the first step), marked not complete, and the next due run tries again. It prints one summary line (a run that removed nothing and waited prints only its waiting line). *M06-AC-2, M06-AC-3.*
3. **The loop holds below the threshold.** With `~/.config/noodlebot/housekeeping` present (read each tick), each tick runs `disk.py check` (under `timeout`, as `pickup.py` is run) before the throttle's decision. While it says hold, the loop treats starts as while the throttle holds, whether or not the throttle is on: no node, triage, update, feedback, adoption or follow-up session starts, no idle session is resumed, the start queue does not ask for a turn, and a `RELEASE` marker starts its node as it does under the throttle. Running sessions go on; as they end, the machine drains and the image step gets its moment. Engaging and releasing are one status-log line each, the engaging line with the hold's reason. A check that fails is one status-log line (not repeated while it keeps failing) and holds nothing. *M06-AC-4, M06-AC-5.*
4. **The loop starts housekeeping.** With the file present, each tick starts `disk.py housekeep` in the background (with the loop's lock closed, as a session's start does) unless the one it started last is still running; the tick does not wait for it. When it has ended, its summary or waiting line, when it printed one, is one status-log line starting `housekeeping:`; a waiting line is not repeated until it changes. *M06-AC-5.*
5. **Without the file nothing changes.** No `disk.py` runs, no `disk.json` or `housekeeping.json` is written, no `podman` is called and the free space holds nothing. `loops.sh start` already passes the `SCHED_*` settings to every loop, and `deploy.sh`'s `make test` runs without them. *M06-AC-6.*
6. **The status issue.** `report.py` adds a Disk line to the status table from `disk.json` when it exists: the free space, the size and the path; "**holding new sessions**: <reason>" while it holds; and from `housekeeping.json` the last run's local time, the space it freed, when any the count of folders it could not remove, and when any "kept N images built here, X GB". The start clause of a waiting unit names the disk hold with its reason, as it names the throttle's. The disk hold's engaging and releasing lines and the `housekeeping:` lines are event comments of the day's log issue. With no `disk.json`, the body is unchanged. *M06-AC-7.*
7. **The README** gets the `housekeeping` row in its table of files under `~/.config/noodlebot/` and the settings `SCHED_DISK_MIN_GB` (GB of 10^9 bytes), `SCHED_HOUSEKEEP_EVERY` and `SCHED_BUILD_TMP`, and says that images built on the machine are kept and shown on the Disk line.

## Risks
- The check reads the filesystem of the runtime root only. Podman's storage (`~/.local/share/containers`) and `/var/tmp` are on it on this machine (`/`, 89% used and 8 GB free on 2026-11-27); where they lie on another filesystem, the hold does not see that one.
- Images built on the machine are never removed, so they can fill the disk on their own (six unused `localhost/` images, about 3.6 GB, on 2026-11-27). The Disk line shows how many are kept and their size; the owner removes them by hand.
- An image is removed only when it has a digest at a registry other than `localhost/`, so it can be pulled again; a session that needs it later pulls it, and fails while the registry is down. The image step runs only with no session under the runtime root and reads the count again before each `rmi`, but a session that starts in the seconds between that read and the `rmi` can still find its image gone and pull it again.
- `podman rmi <id>` without `--force` refuses an image that several names point at; such an image is kept and recorded as skipped, so a few pullable images can stay until the owner removes them.
- On a machine that always runs a session the image step waits; the folder step still runs, and the disk hold drains the machine, so the image step runs at the latest while the disk holds.
- Merged nodes' evidence in the runtime root's `archive/` and build output in long-lived worktrees (a cargo `target/`, say) are not touched: how long to keep them is the owner's choice. The hold sees the space they take and names the low disk, but housekeeping frees none of it.
- A folder owned by another user is left by rule, and the user's own folders owned by subordinate ids inside need `podman unshare`; an unprivileged test cannot make a folder of another owner, so the owner check is shown by the code and the review, not a test.
- The default threshold, 5 GB, is a guess at what a session needs (a worktree and a container build); the owner sets `SCHED_DISK_MIN_GB` for the machine. A hold that never releases because nothing frees space shows on the status issue with its reason; the owner frees space or lowers the threshold.
- A loop started before this node is deployed runs the old loop until its re-exec; the file does nothing until then.
