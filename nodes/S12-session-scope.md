**Owns:** in `scheduler/run-session.sh`: the start of the harness's first stage in a unit of its own (the `systemd-run --user --scope` call, its memory properties and its fallback), the `oom_score_adj` raise, and the record of the unit's result (`session.unit`); in `scheduler/loop.sh`: reading `~/.config/noodlebot/units` and the memory settings (`SCHED_MEMORY_MAX`, `SCHED_SWAP_MAX`, `SCHED_OOM_ADJ`) and handing them to `run-session.sh`, the out-of-memory reason of `record_stop` and the out-of-memory wording of the end lines (`ended`, `feedback_ended`, `triage_ended`, `update_ended`, `adopt_ended`), their lines in the header comment; in `scheduler/report.py`: the out-of-memory milestone on a unit's home issue; `scheduler/loop-s12.test.sh` (new) and `scheduler/run-session-s12.test.sh` (new), their lines in the `Makefile`'s `TESTS`, and any fixtures they add under `scheduler/testdata/s12/`.
**Resolves:** #218

## Purpose
After this node an out-of-memory kill in one session takes that session only, never its loop, the tmux server or another repository's loop. With `~/.config/noodlebot/units` present and `systemd-run --user` working, the agent CLI and every process it starts (subagents, test runners, scripts) run in a systemd user scope of their own with a memory ceiling, so the kernel's OOM killer acts inside that scope. In every mode the session's processes get a raised `oom_score_adj`, so a machine-wide OOM picks a session before a loop, the API or the tmux server. The loop records such an end like any other session that died, naming the out-of-memory kill and the ceiling in the stop reason, `status.log`, the unit's home issue and the resumed run's prompt, and carries on.

## Changes
1. **A unit per session.** `loop.sh` reads `~/.config/noodlebot/units` (its presence turns the systemd user units on; the file holds nothing this node reads) and the settings `SCHED_MEMORY_MAX` (default half of the machine's `MemTotal`), `SCHED_SWAP_MAX` (default half of `SwapTotal`) and `SCHED_OOM_ADJ` (default 500), in systemd's size syntax, `infinity` turning a ceiling off, and hands them to `run-session.sh`. With the units on, `run-session.sh` starts the harness's first stage through `systemd-run --user --scope --unit <name>` with `MemoryMax` and `MemorySwapMax`, the name made of the repository's runtime name, the unit's kind and key and the start time; `systemd-run` execs the command, so the agent CLI stays a direct child of `run-session.sh` and the loop's process-group stop and `agent.pid` work as before. `run-session.sh` itself, which writes `session.rc`, and the harness's record stage stay outside the scope. When the units are off or `systemd-run --user` cannot create a scope, the harness starts directly, with one stderr line. *S12-AC-1, S12-AC-3.*
2. **A raised OOM score.** Before the harness starts, `run-session.sh` raises its own `oom_score_adj` to `SCHED_OOM_ADJ` (only raising, which needs no privilege), so the agent CLI and its children inherit it in every mode. *S12-AC-2.*
3. **The unit's result.** After the first stage exits, `run-session.sh` reads the scope's `Result` (`systemctl --user show -p Result --value <unit>`), writes `session.unit` (`<unit> <result> <MemoryMax>`) next to `session.rc`, and resets the unit when it failed, so failed scopes do not pile up. *S12-AC-1.*
4. **The loop records it.** `record_stop` gives the reason "out of memory in its unit (MemoryMax <ceiling>, rc <rc>)" when `session.unit` holds `oom-kill`, before its other reasons; the end lines of node, feedback, triage, update and adoption sessions name it the same way; the start is counted as for any other end without a PR or question, and the loop goes on with its tick. The resume prompt's `@REASON@` (S04) carries the reason. `report.py` posts one milestone on the unit's home issue for such an end, naming the out-of-memory kill and the ceiling. *S12-AC-4, S12-AC-5.*
5. The settings and the units file get their lines in `loop.sh`'s header comment. `loops.sh start` already passes every `SCHED_*` setting to each loop.

## Risks
- The units are off unless the owner creates `~/.config/noodlebot/units`, so the tests (whose `HOME` is a scratch folder) never create real scopes on the machine that runs them; the owner turns it on once per machine.
- `systemd-run --user` needs the user manager's bus (`XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`); a loop started from a tmux server that lacks them falls back to the OOM score alone, which the stderr line in `session.stderr` shows. In the container (D06) there is no user manager: the OOM score is the protection there.
- `MemorySwapMax` needs swap accounting in cgroup v2; where the kernel lacks it the property is ignored by systemd and only `MemoryMax` holds.
- Half the RAM per session still lets two sessions together fill the machine; the raised OOM score makes the kernel pick a session then, and S13's machine budget caps how many run.
- A scope's `Result` is read once after the exit; a user manager restarted in between loses it, and the end is then recorded by its exit code alone.
- A test runner killed inside the scope can leave a half-done change in the worktree (a mutation script between its edit and its restore); S04's leftover-changes step saves and cleans it before a resume, and D18 tells sessions to restore on every exit.
