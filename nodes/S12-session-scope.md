**Owns:** in `scheduler/run-session.sh`: the start of the harness's first stage in a unit of its own (the `systemd-run --user --scope` call, its memory and stop properties and its fallback), the `oom_score_adj` raise, the end of the first stage (stopping the scope, or killing what is left of the session's process group), the session's scratch folder (`TMPDIR`, `<state-dir>/tmp`), and the record of the unit's result (`session.unit`); in `scheduler/loop.sh`: reading `~/.config/noodlebot/units` and the memory settings (`SCHED_MEMORY_MAX`, `SCHED_SWAP_MAX`, `SCHED_OOM_ADJ`) and handing them to `run-session.sh`, the out-of-memory reason of `record_stop` and the out-of-memory wording of the end lines (`ended`, `feedback_ended`, `triage_ended`, `update_ended`, `adopt_ended`), their lines in the header comment; in `scheduler/report.py`: the out-of-memory milestone on a unit's home issue; `scheduler/loop-s12.test.sh` (new) and `scheduler/run-session-s12.test.sh` (new), their lines in the `Makefile`'s `TESTS`, and any fixtures they add under `scheduler/testdata/s12/`.
**Resolves:** #218

## Purpose
After this node an out-of-memory kill in one session takes that session only, never its loop, the tmux server or another repository's loop, and a session leaves nothing running or filling memory behind it. With `~/.config/noodlebot/units` present and `systemd-run --user` working, the agent CLI and every process it starts (subagents, test runners, scripts) run in a systemd user scope of their own with a memory ceiling, so the kernel's OOM killer acts inside that scope. In every mode the session's processes get a raised `oom_score_adj`, so a machine-wide OOM picks a session before a loop, the API or the tmux server. When the session's first stage (the agent CLI) ends, every process it left (a test's server, an orphan) is killed: the scope is stopped, or without a unit the rest of the session's process group is killed. Each session's `TMPDIR` is a folder on disk under the runtime root, not the RAM-backed `/tmp`, removed when the session ends. The loop records an out-of-memory end like any other session that died, naming the out-of-memory kill and the ceiling in the stop reason, `status.log`, the unit's home issue and the resumed run's prompt, and carries on.

## Changes
1. **A unit per session.** `loop.sh` reads `~/.config/noodlebot/units` (its presence turns the systemd user units on; the file holds nothing this node reads) and the settings `SCHED_MEMORY_MAX` (default half of the machine's `MemTotal`), `SCHED_SWAP_MAX` (default half of `SwapTotal`) and `SCHED_OOM_ADJ` (default 500), in systemd's size syntax, `infinity` turning a ceiling off, and hands them to `run-session.sh`. With the units on, `run-session.sh` starts the harness's first stage through `systemd-run --user --scope --unit <name>` with `MemoryMax`, `MemorySwapMax` and a short `TimeoutStopSec` (at most 5 s, so a stop that SIGTERM does not finish ends in SIGKILL), the name made of the repository's runtime name, the unit's kind and key and the start time; `systemd-run` execs the command, so the agent CLI stays a direct child of `run-session.sh` and the loop's process-group stop and `agent.pid` work as before. `run-session.sh` itself, which writes `session.rc`, and the harness's record stage stay outside the scope. When the units are off or `systemd-run --user` cannot create a scope, the harness starts directly, with one stderr line. *S12-AC-1, S12-AC-3.*
2. **A raised OOM score.** Before the harness starts, `run-session.sh` raises its own `oom_score_adj` to `SCHED_OOM_ADJ` (only raising, which needs no privilege), so the agent CLI and its children inherit it in every mode. *S12-AC-2.*
3. **The unit's result.** After the first stage exits and its scope is stopped (Change 6), `run-session.sh` reads the scope's `Result` (`systemctl --user show -p Result --value <unit>`), writes `session.unit` (`<unit> <result> <MemoryMax>`) next to `session.rc`, and resets the unit when it failed, so failed scopes do not pile up. *S12-AC-1.*
4. **The loop records it.** `record_stop` gives the reason "out of memory in its unit (MemoryMax <ceiling>, rc <rc>)" when `session.unit` holds `oom-kill`, before its other reasons; the end lines of node, feedback, triage, update and adoption sessions name it the same way; the start is counted as for any other end without a PR or question, and the loop goes on with its tick. The resume prompt's `@REASON@` (S04) carries the reason. `report.py` posts one milestone on the unit's home issue for such an end, naming the out-of-memory kill and the ceiling. *S12-AC-4, S12-AC-5.*
5. The settings and the units file get their lines in `loop.sh`'s header comment. `loops.sh start` already passes every `SCHED_*` setting to each loop.
6. **Nothing left running.** As soon as the first stage exits (not when the record stage ends, which a leftover process holding the first stage's output would delay), `run-session.sh` ends what the session left: with a scope, `systemctl --user stop <unit>`, which kills every process in it, SIGKILL after the scope's `TimeoutStopSec`; without one, or when the stop fails, SIGTERM to every process of the session's process group (`setsid` made `run-session.sh` its leader) but `run-session.sh` itself and the record stage, then SIGKILL after a grace of 3 s, as the loop's `stop_group` does. It returns at once when nothing is left. *S12-AC-6.*
7. **Scratch on disk.** Before the harness starts, `run-session.sh` empties or makes `<state-dir>/tmp` (under the runtime root, on disk) and exports it as `TMPDIR` to the harness in every mode; after Change 6 it removes the folder, whatever the exit code. A folder it cannot make leaves the inherited `TMPDIR` and one stderr line. *S12-AC-7.*

## Risks
- The units are off unless the owner creates `~/.config/noodlebot/units`, so the tests (whose `HOME` is a scratch folder) never create real scopes on the machine that runs them; the owner turns it on once per machine.
- `systemd-run --user` needs the user manager's bus (`XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`); a loop started from a tmux server that lacks them falls back to the OOM score alone, which the stderr line in `session.stderr` shows. In the container (D06) there is no user manager: the OOM score is the protection there.
- `MemorySwapMax` needs swap accounting in cgroup v2; where the kernel lacks it the property is ignored by systemd and only `MemoryMax` holds.
- Half the RAM per session still lets two sessions together fill the machine; the raised OOM score makes the kernel pick a session then, and S13's machine budget caps how many run.
- A scope's `Result` is read once after the stop; a user manager restarted in between loses it, and the end is then recorded by its exit code alone.
- Without a unit, a process that left the session's process group (`setsid`, a daemon) survives the end; only a scope catches it. A process the session meant to outlive it has nowhere to go: a session's work ends with the session.
- A fake harness in an existing loop test that leaves a background process meant to outlive the first stage would see it killed now; S12-AC-3 holds those tests unchanged, so such a case goes to the owner rather than being edited.
- A `TMPDIR` under the runtime root is longer than `/tmp`: a test that makes a Unix socket in a scratch folder under it comes closer to the 108-byte path limit. Files that podman's subordinate ids made in the folder need `podman unshare rm -rf`; whatever stays is emptied at the unit's next start.
- A test runner killed inside the scope (an OOM kill, a SIGKILL) runs no trap, so a mutant applied in the worktree would stay there; D18 has sessions apply mutants only in a scratch copy of the tree, never in the node's own worktree, so such a kill leaves the worktree as it was.
