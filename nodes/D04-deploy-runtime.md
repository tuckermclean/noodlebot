**Owns:** in `scheduler/deploy.sh`: the runtime-path list and its check (`--runtime-changed`), the fast-forward without `make test`, the rerun of failed files and the flaky record, the kept log `deploy/test-failed.log` and the stderr lines naming failed files, and their lines in the header comment; `scheduler/deploy-d04.test.sh` (new) and its line in the `Makefile`'s `TESTS`; in `scheduler/loop.sh`: the re-exec condition after a deploy and its line in the header comment; `scheduler/loop-d04.test.sh` (new) and its line in the `Makefile`'s `TESTS`; in `scheduler/runtests.sh`: the `FAILED <file>` line and its header-comment line, and its case in `scheduler/runtests.test.sh`.
**Resolves:** #92

## Purpose
After this node the self-deploy spends `make test` and a loop restart only on commits that change what the loop runs, and a flaky test no longer refuses a good commit for good. A range of commits that touches only specs, the graph, docs or CI workflows is fast-forwarded into the live checkout without a test run and without re-execing the loops. A `make test` that fails reruns just its failed files, one at a time; a failure that does not repeat is deployed and recorded as flaky. Every failing run leaves its output behind, and `deploy.log` names the files that failed.

## Tests
- `scheduler/deploy-d04.test.sh` (new, in the style of `scheduler/deploy.test.sh`: a fake remote of the scheduler's own repository, the live checkout as a clone, `make test` stubbed per commit and recording each call with its arguments and its `TEST_JOBS`): a commit that changes only non-runtime paths, one that also changes `scheduler/`, a range of two commits of which only the first is runtime, a commit with a new top-level path, a commit whose stub fails a file on the first run and passes it alone, one whose stub fails the same file twice, and one whose stub fails without naming a file.
- `scheduler/loop-d04.test.sh` (new, in the style of `scheduler/loop-d01.test.sh`): a running loop with a session, given a non-runtime commit and then a runtime commit on its remote; its pid, its status-log lines and its session after each.
- `scheduler/runtests.test.sh` (extended): the `FAILED <file>` line for a failing fake file, and none for a passing one.

## Changes
1. **The runtime-path list.** `deploy.sh` holds one list of the paths that are not runtime, each with a comment giving the reason:
   - `SPEC.md`, `AGENTS.md`, `CLAUDE.md`, `README.md`: read by people, and by sessions from their own worktrees, never by a loop from the live checkout.
   - `docs/`: the loop reads `docs/graph.yaml` from `origin/main` of its clone (`repos/<name>`), not from the live checkout.
   - `nodes/`: the loop, `report.py` and `site.py` read node specs from `origin/main` of the clone; sessions read them in their worktrees.
   - `.github/`: the workflows run on GitHub's runners, never on the scheduler's machine.

   Every other path is runtime, and the header comment says why for the rest: `scheduler/` (the loop, its helpers, the session templates and the test files `make test` runs), `plugin/` (every session loads the live checkout's plugin, `--plugin-dir`), `site/` (the status site's front end and its tests in `make test`), the `Makefile` (the deploy's own `make test`), `.claude/` (the role agents of a session started in the live checkout) and any path the list does not name, so a new top-level path is runtime until a spec change lists it. `deploy.sh --runtime-changed <live checkout> <from> [<to>]` (default `<to>` is `HEAD`) exits 0 when `git diff --name-only <from> <to>` names a runtime path, 1 when it names none, and 2 when git fails, so the loop and `deploy.sh` use the one list. *D04-AC-1, D04-AC-2, D04-AC-3.*
2. **A non-runtime range is fast-forwarded without `make test`.** When the live checkout's `HEAD` can fast-forward to a new, not rejected `origin/main` and the range `HEAD..origin/main` changes no runtime path, `deploy.sh` fast-forwards without a scratch worktree or `make test`, leaves `deploy/previous` as it is (the rollback point stays the commit before the last runtime deploy) and prints one line `deployed <old>..<new> (version <v>) without make test: no runtime change`. A range with any runtime change, wherever it is in the range, gets the full deploy as before. *D04-AC-1, D04-AC-2.*
3. **The loop re-execs only for a runtime change.** After its deploy step, a loop re-execs only when `deploy.sh --runtime-changed` reports a runtime change between the commit it started on and the checkout's `HEAD`; when the check fails (status 2) it re-execs, as today. A loop that does not re-exec keeps its start commit, its version and its sessions, and a later runtime deploy re-execs it as before. *D04-AC-3.*
4. **The runner names its failed files.** `scheduler/runtests.sh` prints `FAILED <file>` after the `TIME` line of each file that exited non-zero; nothing else in its output changes. *D04-AC-4.*
5. **A failed `make test` is rerun once, alone.** When `make test` fails (not a timeout, a signal, or status 125–127, which keep their handling), `deploy.sh` reads the `FAILED <file>` lines of its output and, in the same scratch worktree and the same cleaned environment, runs `make test TESTS="<those files>"` once with `TEST_JOBS=1`, under a timeout no longer than the first run's. If the rerun passes, the commit is deployed as on a pass, the status line is `deployed <old>..<new> (version <v>) after a flaky make test: <n> file(s) failed and passed alone`, and `deploy.sh` writes one stderr line (so one `deploy.log` line) `flaky: <sha> <files> failed in make test and passed alone; log in <path>`. If the rerun fails in any way, or the first run named no failed file, the commit is rejected as before with the unchanged line `not deployed: <sha> (version <v>) fails make test`. *D04-AC-4, D04-AC-5.*
6. **The failing run's output is kept.** Before the scratch folder is removed, the output of a failed `make test` and of its rerun is written to `$NOODLEBOT_DATA/deploy/test-failed.log` (a temporary file renamed over the old one, so it always holds the last failing run whole), headed by the commit, its version, the UTC time and the outcome (`rejected` or `flaky`). The shared `deploy/` folder is used, not one loop's `state/<name>/`, because one `deploy.sh` run under the lock serves every loop. On a rejection `deploy.sh` writes one stderr line `make test failed for <sha> in: <files> (or "no file named"); log in <path>`, so the loop's `deploy.log` names the failed files. *D04-AC-6.*

## Gate
- **D04-AC-1** — A new `origin/main` whose range from the live checkout's `HEAD` changes only the listed non-runtime paths is fast-forwarded without running `make test` (the stub records no call), with one status line `deployed <old>..<new> (version <v>) without make test: no runtime change`, and `deploy/previous` unchanged. *Verify:* `scheduler/deploy-d04.test.sh`.
- **D04-AC-2** — A range with any runtime change gets `make test` before it is deployed: a commit that also changes `scheduler/`, a range of two commits whose first is runtime and second is not, and a commit that adds a new top-level path each run the stub, and each is rejected when it fails. *Verify:* `scheduler/deploy-d04.test.sh`.
- **D04-AC-3** — A running loop given a non-runtime commit moves its checkout to it and does not re-exec: the same pid, no new `loop started` line, its session still owned; given a runtime commit after that, it re-execs within one tick as D01 says. `deploy.sh --runtime-changed` exits 0, 1 and 2 as Change 1 says. *Verify:* `scheduler/loop-d04.test.sh` (the loop) and `scheduler/deploy-d04.test.sh` (the exit statuses).
- **D04-AC-4** — `scheduler/runtests.sh` prints `FAILED <file>` for each file that exited non-zero and none for a passing file. A `make test` that fails a file that passes alone is followed by exactly one rerun, of only the failed files, with `TEST_JOBS=1`; the commit is deployed with the `after a flaky make test` status line, is not in `deploy/rejected`, and one `flaky:` stderr line names the sha and the files. *Verify:* `scheduler/runtests.test.sh` (the line) and `scheduler/deploy-d04.test.sh` (the rerun, via the stub's recorded calls).
- **D04-AC-5** — A failure that repeats on the rerun, or a failed `make test` that names no failed file, is rejected exactly as D01 says (the unchanged `not deployed: … fails make test` line, the sha in `deploy/rejected`, not tried again), with no more than one rerun. *Verify:* `scheduler/deploy-d04.test.sh`.
- **D04-AC-6** — After a rejection or a flaky deploy, `deploy/test-failed.log` holds that run's output (with the rerun's) under a header naming the sha, its version and the outcome, the scratch folder is gone, and on a rejection one stderr line names the failed files and the log's path. *Verify:* `scheduler/deploy-d04.test.sh`.

## Risks
- A runtime path the list misclassifies as non-runtime would be deployed untested and not restart the loops; the list is short and everything it does not name is runtime, so a mistake errs towards testing.
- A loop that skips a re-exec keeps its version, so its signature names the last runtime commit, not the live checkout's `HEAD`. That is the code it runs, so this is correct, but `git describe` of the checkout and the loop's version can differ.
- A test that fails under load and passes alone is deployed. That is the intent for timing flakes (D05 makes the S07 cases robust), but a real race that shows up only under load is deployed too; the `flaky:` lines in `deploy.log` and the kept log are where the owner sees it.
- The rerun holds the deploy lock longer; another loop's `deploy.sh` waits up to five minutes and then gives up for that tick, which only delays it.
- `api.py` and `site.py` read the `deployed` and `not deployed:` lines by their prefixes and the ` fails make test` ending; the new lines keep those prefixes, and the rejection line is unchanged.
