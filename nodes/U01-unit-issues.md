**Owns:** in `scheduler/report.py`: each unit's home issue (its choice, the Build issue, the record `node/<ID>/issue` and `issue/<N>/issue`), the milestone comments, answers taken on home issues, closing and reopening home issues and the other issues a merged node resolves, and the status issue's links to them in place of the questions it posted; the `noodlebot-unit` label in `scheduler/labels.py`; the answering and closing-keyword lines of `scheduler/unattended.md`, `scheduler/unattended-triage.md` and `scheduler/unattended-followup.md`; the lines on what the node's PR says about its issues in `plugin/skills/triage/SKILL.md` and `plugin/skills/adopt/SKILL.md`; the README's sections on handing an issue to the bot and answering a question; their cases in `scheduler/report.test.sh`, `scheduler/labels.test.sh` and `scheduler/loop.test.sh`.
**Resolves:** #23

## Purpose
After this node each unit of work, a triage or a node while it is built, has one GitHub issue of its own, and its questions and milestones are posted there instead of among the events on the status issue. A triage uses the issue it triages; a node uses the first issue on its spec's **Resolves:** line, or a new "Build <ID> <name>" issue when it has none. The loop posts only milestones there, each starting with a stage line, and any comment by the owner after the unit's open question is its answer, with no ID prefix. The loop closes an issue itself once every node resolving it is merged and no question is open, so PR bodies refer to issues without a closing keyword. The status issue (until U02 replaces it) keeps the events and links to each unit's issue.

## Changes
1. **Each unit has a home issue.** `report.py` records a unit's home issue in its state folder (`node/<ID>/issue`, `issue/<N>/issue`) the first time it posts a milestone for it, and keeps that number afterwards. A triage of issue N uses N. A node uses the first issue number on the **Resolves:** line of its spec on `origin/main`; its first milestone comment links the other issues on that line. A node with no Resolves line gets a new issue titled "Build <ID> <name>", labelled `noodlebot-unit`, whose body names the node's spec and says the loop closes it once the node is merged. *U01-AC-1.*
2. **Milestones, not ticks.** On a unit's home issue `report.py` posts only these milestones, each once: started or resumed (with the start count; resumed when the unit has `answered/`); a question, as its own comment holding the whole QUESTION.md; answer received; for a node, its PR opened (link), the CI result of each PR head commit once all its check runs are complete (passed, or failed with the failing checks' names), and each fresh-review verdict (a PR comment headed `Fresh review (`); merged, or closed without merging; FAILED with the first line of its FAILED file; for a triage, done (with its spec PR, if a `spec/triage-<N>-*` PR exists). Every milestone comment starts with a stage line that says where the unit is ("PR #12 open, final review running", say). `report.json` records what was posted per unit, so a failed post is retried on the next run and nothing is posted twice. On its first run after this change it posts no milestone for events or questions from before. *U01-AC-2, U01-AC-3, U01-AC-9.*
3. **Answers on the home issue.** A comment by the owner (the `--owner` login with association OWNER, not a bot) on a unit's home issue, created after the comment that posted the unit's open question, becomes that unit's ANSWER.md, in today's format with the comment's URL and no ID prefix needed. The loop adds a `+1` reaction to it and posts the answer-received milestone, whose stage line says what the answer waits for as S03 says it. It replies only when it cannot use a comment: when no unit on that issue has a question open, and when more than one has and the comment does not start with one's ID. Comments before the unit's first milestone, and anyone else's, are ignored. Prefixed answers on the status issue are still taken as now; a question answered on either issue is not recorded again from the other. *U01-AC-4, U01-AC-5.*
4. **The loop closes the issues it resolves.** Once a node's PR is merged, `report.py` closes each issue on the node's Resolves line, and the node's Build issue, with a last comment naming the merged PR(s), when every node whose Resolves line names that issue is merged, no unit whose home it is has a question open (QUESTION.md without ANSWER.md), and none has a follow-up in progress (S03's FOLLOWUP marker or an answered question not yet released). A triage never closes its issue. A new question of a unit whose home issue is closed reopens the issue before it is posted, and the issue closes again by the same rule. *U01-AC-6.*
5. **Triage on the triaged issue.** A triage's questions, answers and milestones are on the issue it triages; the status issue no longer shows a triage's question in full. *U01-AC-7.*
6. **The status issue links instead of posting questions.** The status issue's "Waiting on you" items link the unit's question comment on its home issue, and no QUESTION.md is posted in full there; its events stay. Its footer says to answer on the unit's issue and that a prefixed reply there still works. *U01-AC-7.*
7. **Prompts and skills.** `scheduler/unattended.md`, `scheduler/unattended-followup.md` and `scheduler/unattended-triage.md` end a QUESTION.md with "To answer: reply on this unit's issue (the loop posts the question there)." instead of a status-issue prefix. The node and follow-up prompts have the PR body name each issue on the spec's Resolves line as "Refs #N" and write no closing keyword anywhere; the triage and adopt skills say the loop closes the resolved issues once the nodes are merged, and drop "the node's PR fixes it". *U01-AC-8.*
8. **The label.** `labels.py` also ensures `noodlebot-unit` ("A unit of noodlebot work, while it is built"). *U01-AC-10.*
9. **README.** "Handing an issue to the bot" and "Answering a node's question" describe home issues, milestones, answering without a prefix and the loop closing issues.

- **U01-AC-4** — An owner's comment on a unit's home issue posted after its open question becomes that unit's ANSWER.md (with the comment's URL) without an ID prefix, gets a `+1` reaction and the answer-received milestone, and no other reply. A comment from before the question, or by someone else, is not recorded and gets no reply. With no question open on that issue, an owner's comment is not recorded and gets one reply saying so. With two units on the issue both waiting, an unprefixed comment is not recorded and gets one reply naming them, and one starting with an ID is that unit's answer. *Verify:* `scheduler/report.test.sh`.
- **U01-AC-5** — A prefixed answer on the status issue is still recorded as now; once a question is answered on either issue, a later comment on the other is not recorded as its answer. *Verify:* `scheduler/report.test.sh`.
- **U01-AC-6** — After a node's PR is merged, `report.py` closes its home issue, its Build issue and every other issue on its Resolves line, each with one comment naming the PR, only when every node resolving that issue is merged and no unit whose home it is has an open or unreleased answered question or a follow-up in progress; it leaves the issue open otherwise and closes it at the first run after that holds. It never closes the issue of a triage. A new QUESTION.md of a unit whose home issue is closed reopens that issue and posts the question there. *Verify:* `scheduler/report.test.sh`.
- **U01-AC-7** — The status issue posts no QUESTION.md in full (a node's or a triage's): its "Waiting on you" item for an open question links the question's comment on the unit's home issue, and its events are posted as before. *Verify:* `scheduler/report.test.sh`.

- **U01-AC-9** — When a GitHub call fails while `report.py` creates a Build issue or posts a milestone, the run logs it and exits non-zero, the loop carries on, and the next run creates or posts it once; the first run after this change posts no milestone for status-log events, questions or PRs from before it. *Verify:* `scheduler/report.test.sh`.
- **U01-AC-10** — `labels.py ensure` creates `noodlebot-unit` when it is missing and leaves an existing one unchanged. *Verify:* `scheduler/labels.test.sh`.

## Risks
- The owner's own issues get bot comments: the milestones are the whole list, but a node with several pushes posts one CI result per head commit, and a busy node may post a dozen comments in a day.
- An owner comment on a unit's issue that is not meant as an answer is taken as one when a question is open, and gets a reply when none is. The comment is still on the issue for the owner to correct with a new answer.
- Closing issues moves from GitHub's closing keywords to the loop: while the loop is not running, a merged node's issues stay open until it runs again. Issues on a Resolves line that are not the node's home were closed by "Fixes #N" before; now the loop closes them by the same rule as the home issue.
- A node's home issue is chosen from the spec on `origin/main` when its first milestone is posted; a later spec change to its Resolves line does not move it.
- Units in flight when this ships get their home issue at their next milestone; questions already posted on the status issue are answered there, with the prefix.
- G01's spec-PR updates (`PR #N` tasks) are not units: they have no home issue and stay on the status issue. Issue #35's noodlebot version goes on the start milestone when that issue's node lands.
- Each run reads check runs and comments of every open node PR: more `gh api` calls per tick, under the App's rate limit.
